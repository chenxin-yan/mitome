Mitome runs code you wrote, with the access you have, against services that bill your account. This page states the trust boundaries so you know what to protect.

## A Mitome Definition is a program

A [Mitome Definition](/docs/concepts#agent-definition-and-mitome-definition) is executable TypeScript, not a configuration file. When you run `mitome`, the CLI starts a **Child Host** process that imports the Definition module, the Hosts it declares, and every dependency in its `package.json`. That process has your filesystem, your network, your environment variables, and every Credential the Definition's Providers can reach.

Run only Mitome Definitions you trust. `mitome --use <path>` executes whatever module is at that path, and `mitome add <package>` installs and later imports whatever that package publishes. Neither the CLI nor a Host sandboxes the code. Treat a Mitome Definition and its dependencies the way you treat any script you would run with your own account.

The same holds when you embed the SDK: an Extension's Tool handlers run in your application process with its permissions.

## Tools act on your behalf

A Tool call is the Model deciding to run your code. Three mechanisms gate it: `preTool` Hooks apply policy an Extension author wrote, the Agent's `approvals` applies the Agent author's policy, and whatever still asks becomes an Approval the Host resolves. Core enforces every `deny` and veto itself; an ask is a request for a person. The [TUI](/docs/tui) prompts for it, and one-shot output (`mitome -p`, or any non-TTY run) denies it with a reason the Model sees, because nobody is there to answer.

Three switches relax that, and it matters what each does not bypass:

| Switch                       | Set by                     | Skips the Tool's `needsApproval` predicate | Answers `policy` asks | Beats `deny` or a `preTool` veto |
| ---------------------------- | -------------------------- | ------------------------------------------ | --------------------- | -------------------------------- |
| `approvals.allow` in Agent   | The Agent author           | Yes; the predicate is not evaluated        | No                    | No                               |
| `mitome --yes`               | Whoever runs it            | No; a failed predicate is still denied     | No                    | No                               |
| TUI "allow for this Session" | The person at the terminal | No                                         | No                    | No                               |

`allow` is the Agent author's standing decision and is visible in the Agent Definition; `--yes` is a per-invocation decision by whoever runs the command and only covers requests the Tool author flagged (`requirement: "tool"`). The TUI's Session grant is the same scope as `--yes`, held for one live Session on one terminal. None of them turns a `deny`, a veto, or a policy `ask` into a run. For Tools with real side effects, mark them `needsApproval` and run them where a person can answer, as the [Approvals](/docs/approvals) page explains.

## Credentials

A [Credential](/docs/concepts#credential) authorizes Mitome to spend on your account. Keep it in exactly one place: the environment variable or `<config-dir>/auth.json` entry its Provider reads. Never:

- paste it into `index.ts` or any Agent Definition;
- put it in Instructions, where it becomes Model input;
- return it from a Tool handler, where it becomes Model input and a Turn event;
- throw it inside an error, where it can reach logs; a Tool handler that throws produces an opaque failure, but a rejected `withSession` callback surfaces the error unchanged;
- commit `.env` or `auth.json`, or include them in backups, logs, or bug reports.

The CLI writes `.env` and `auth.json` readable by you alone, and reads `.env` only into the Child Host process. Embedded applications never read `.env`; supply the variable from your platform's secret manager. The full precedence and every file's mode are listed under [Configuration](/docs/configuration#credentials).

## What is persisted

With `transcripts` declared, every completed Turn's Messages and every Turn event, including Tool inputs and results, are written to the store. A Transcript is user data plus whatever your Tools returned; place the store accordingly and treat what you read back as untrusted input, as [Custom Transcript store](/docs/custom-transcript-store#validate-what-you-read) describes. Without `transcripts`, Mitome writes nothing.
