An [Extension](/docs/concepts#extension) is what an Agent Definition includes to change how the Agent behaves. It can contribute [Instructions](/docs/concepts#instructions), declare [Tools](/docs/tools), hold a private Resource for the Session's lifetime, and observe or transform the run through Hooks. Use one instead of inline `defineAgent({ tools })` as soon as Tools need shared state, when you want Instructions to travel with the Tools that need them, or when several Agents should reuse the same behavior.

```ts
import { defineAgent } from "@mitome/sdk";
import { instructions } from "@mitome/sdk/extensions";
import { openai } from "@mitome/providers/openai";

const agent = defineAgent({
  providers: [openai()],
  model: "openai/gpt-5.4-mini",
  extensions: [instructions("Answer in one short paragraph.")],
});
```

Extensions are applied in the order you list them: Instructions are composed in that order, Resources are acquired in that order, and start Hooks run in that order.

## Instructions

Two first-party Extensions in `@mitome/sdk/extensions` cover static Instructions:

- `instructions(text)` contributes the text as-is.
- `instructionFiles({ paths, discover })` reads files when the Mitome Definition loads. `paths` are resolved relative to the module that calls it and must exist. `discover` names bare filenames, such as `AGENTS.md`, looked up in every directory from the Git root down to the current working directory, or only the current directory when there is no Git root; missing ones are skipped.

```ts
import { instructionFiles } from "@mitome/sdk/extensions";

instructionFiles({ paths: ["./AGENTS.md"], discover: ["AGENTS.md"] });
```

Your own Extension contributes Instructions through its `instructions` field, shown below.

## A Resource with Tools

`resource` runs once when a Session starts and returns the Resource. Call `defer` after each step that needs undoing: the cleanups run in reverse registration order when the Session is released, on success, failure, and interruption alike, and even when a later step of `resource` throws, so a half-acquired Resource never leaks. The scoped `tool` builder carries the Resource type into every handler:

<include lang="ts">../../examples/notes-extension.ts</include>

Declare `resource` before `tools` and `hooks`. TypeScript infers the Resource type from its return value, and with the other order it fixes the type to `never` first; annotating the parameter with `ResourceContext` lifts that restriction.

A Resource is private to its Extension. Tools and Hooks that need the same Session state belong in one Extension. A resumed Transcript seeds a new Session, so `resource` runs again and the Resource starts fresh.

### Sharing a service between Extensions

When two Extensions need the same service, create it where the Agent Definition is composed and pass it into each Extension's factory. The application owns its lifetime; each Extension's own `resource` stays private.

```ts
const db = await openDb();
const notes = ({ db }: { readonly db: Db }) =>
  defineExtension({ tools: ({ tool }) => noteTools(tool, db) });
const agent = defineAgent({ providers, model, extensions: [notes({ db }), memory({ db })] });
```

### Test doubles

Keep the definition in a plain object and spread it with a replacement `resource`:

```ts
const definition = {
  resource: async (): Promise<Notes> => openNotes(),
  tools: ({ tool }: { readonly tool: ToolBuilder<Notes> }) => noteTools(tool),
};
export const notes = defineExtension(definition);
export const notesWith = (fake: Notes) =>
  defineExtension({ ...definition, resource: async () => fake });
```

## Hooks

Hooks let an Extension observe or transform the run. Every Hook receives a context with `resource` and `signal`; a rejected Hook fails the Turn, or the Session start, with `TurnError`.

| Hook                          | Contract                                                                                             |
| ----------------------------- | ---------------------------------------------------------------------------------------------------- |
| `sessionStart(context)`       | Runs once after every Extension's Resource is acquired.                                              |
| `sessionEnd(context)`         | Runs when the Session is released, before Resources are released.                                    |
| `turnStart(message, context)` | Observes the user Message that starts a Turn.                                                        |
| `turnEnd(message, context)`   | Observes the user Message after its Turn completed.                                                  |
| `stepStart(prompt, context)`  | Observes the Model Prompt before one Step.                                                           |
| `stepEnd(prompt, context)`    | Receives the Model Prompt and the Step's `responseParts`; a failed Step provides its partial parts.  |
| `preStep(prompt, context)`    | Returns the Model Prompt to send, transformed or unchanged.                                          |
| `preTool(context)`            | Policy before a Tool runs: return `{ reason }` to veto, `"ask"` to require an Approval, or nothing.  |
| `postTool(context)`           | Observes and returns the Tool result, transformed or unchanged; `isFailure` marks expected failures. |

Start Hooks (`sessionStart`, `turnStart`, `stepStart`) run in Agent Definition order. End Hooks (`sessionEnd`, `turnEnd`, `stepEnd`) run in reverse order, mirroring how Resources are released, so an Extension listed first sees the Session both first and last.

```ts
import { defineExtension } from "@mitome/sdk";

export const audit = defineExtension({
  name: "audit",
  hooks: {
    turnStart: async (message) => console.error(`turn: ${JSON.stringify(message)}`),
    preTool: async ({ name }) =>
      name === "delete_file" ? { reason: "deletion disabled" } : undefined,
  },
});
```

A `preTool` veto reaches the Model as a denied execution with your `reason`. Returning `"ask"` instead pauses the call for a Host [Approval](/docs/approvals) with `requirement: "policy"`, even when the Agent's `approvals` would allow it. An Extension can therefore tighten a Tool's Approval requirement but never remove one: the most restrictive opinion wins, and only the Agent author's `allow` overrides a Tool author's own `needsApproval`.

## Names and identity

`name` is optional and only labels diagnostics. An unnamed Extension is identified by its object reference, so including the same value twice is one Extension. Two _different_ named Extensions with the same name conflict and fail the Agent Definition; so do two Tools with the same name in different Extensions; a duplicate within one Extension throws when it is defined.

From a terminal, `mitome ext list` prints the Extensions of the selected Mitome Definition in composition order, with their package versions where known; unnamed ones appear as `(anonymous)`.
