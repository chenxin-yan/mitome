The `mitome` command loads exactly one [application](/docs/applications): the default export of the file passed with `--app`, resolved against the current directory. It never searches a project, home or config directory, never guesses an entry file and never installs dependencies. Loading imports and runs the module, so select only code you trust.

```text
mitome --help
mitome --version
mitome run --app <file> [--provider <id>] [--model <provider/model>] [--grace <duration>] [input]
mitome tui --app <file> [--provider <id>] [--model <provider/model>] [--grace <duration>]
mitome providers --app <file>
mitome auth status --app <file> [--provider <id>]
mitome auth login --app <file> [--provider <id>]
mitome auth logout --app <file> [--provider <id>]
```

## run

`run` is one-shot, in a terminal or not. It acquires the application, allocates one fresh Session, runs one Turn and shuts down.

- **Input.** The `input` argument wins and standard input is then not read. Without it, non-terminal standard input is read to its end as one payload. In a terminal with no argument, `run` reports usage. The text goes through the application's `cli.parseInput`; there is no implicit Message or JSON decoding.
- **Output.** The result goes through `cli.renderResult`, and only that string is written to standard output, followed by one newline unless it is empty or already ends with one. Diagnostics, including the application's own Effect logs and unexpected defects, go to standard error. An application without a `cli` mapping cannot be run.
- **Selection.** `--model` takes a Qualified Model id, split at its first `/`, and never falls back. `--provider` restricts the configured default and fallbacks to one Provider. Unknown Providers, malformed ids and mismatched flags fail before anything is acquired.
- **Exit status.** Load, selection, input, application and rendering failures exit 1. A rendering failure after the Turn committed is reported as such; the Turn is not rerun.

### Shutdown and grace

On SIGINT or SIGTERM the CLI starts a wall-clock grace timer, then cancels cooperatively: admission closes, the active Turn and Hosts are interrupted and their cleanup is awaited before shared infrastructure is released. If cleanup finishes, the exit status is 130. The same timer bounds the cleanup that follows ordinary completion or failure, including the unwind of a startup that failed. One exception: a native Layer that fails while it is being built rolls back its own resources before the application can begin shutting down, so a hanging rollback inside that Layer is bounded only after SIGINT or SIGTERM starts the timer. If the grace expires first, the CLI reports it on standard error and exits 1 without claiming cleanup finished.

`--grace` accepts a positive duration such as `500ms` or `5s` (default `5s`, at most 2147483647ms). A blocked event loop cannot honor it; use an external supervisor for hard limits.

## tui

`tui` is the standalone terminal for one application. It needs a terminal on both standard input and standard output and refuses otherwise, before loading anything. It acquires the application once, allocates one Session and keeps it for every submission until you close the terminal. There is no attachment to another running application.

- **Input and output.** Each submission's text goes through `cli.parseInput`, runs as one Turn and is shown through `cli.renderResult`, exactly as with `run`. Rendered output is application output, not a Message: the committed conversation is only what the program staged, and the status line counts its Messages. A parse failure starts no Turn; a rendering failure after the Turn committed is reported and the Turn is not rerun.
- **One at a time.** A new submission waits until the previous one settles; a draft typed meanwhile is kept. Each submission shows its Turn's outcome from the Session's own record: succeeded and committed, failed, or interrupted, with committed conversation unchanged unless it committed.
- **Approvals.** Only an application that declares `cli.approvals` (see [Applications](/docs/applications#approvals-in-the-terminal)) can be decided from the terminal. A pending Tool Call is shown exactly as the handler would receive it: its Turn, Tool-call id, Tool and decoded parameters, inspected natively with control characters escaped; the box scrolls rather than truncating. Press Tab to focus it, then `y` to approve or `n` to deny; typing or pasting in the editor decides nothing. A denial is recorded on its own line; whether the Turn then fails or continues is up to the program. Without `cli.approvals` the terminal offers no decisions, and the program's own consent still decides.
- **Progress.** The view rereads the pending Approvals about every 100ms and each submission's outcome when it settles. Observation never drives or blocks execution, and there is no token streaming.

| Key       | Effect                                                                                |
| --------- | ------------------------------------------------------------------------------------- |
| Alt-Enter | Submit the editor's text (Enter inserts a newline)                                    |
| Esc       | Interrupt the running submission; its cleanup is shown as continuing until it settles |
| Tab       | Move focus between the editor and a pending Approval                                  |
| `y` / `n` | Approve or deny the focused Approval                                                  |
| Ctrl-C    | Close                                                                                 |

Closing (Ctrl-C, SIGINT or SIGTERM) restores the terminal first and then shuts the application down as described under [Shutdown and grace](#shutdown-and-grace): an active Turn is interrupted and its cleanup awaited. A clean close exits 130; startup and shutdown failures, a terminal failure (a failed frame, or a defect such as a malformed Approval decision) and an expired grace exit 1, the last without claiming cleanup finished. Restoration is cooperative: SIGKILL, a blocked event loop or a failing terminal can still leave it unrestored.

## providers

Lists each declared Provider with its catalog hints and known context windows, then the configured default and fallbacks. Nothing is acquired, provisioned or authenticated. Catalogs are hints: `run --model` accepts any Provider-native id.

## auth

None of the `auth` commands acquire the application, start a Session or provision a Model.

- `auth status` reports offline facts only: whether an environment credential is present or missing (never its value), or that a Provider offers an auth capability whose credential status is unknown.
- `auth login` and `auth logout` act on the Provider named by `--provider`, or on the only Provider that takes a credential. For an environment credential they explain which variable to set or unset; Mitome does not store it. For an auth capability they run the Provider's own login or logout, which may open a browser and needs network access.

Capability credentials are stored in the application's `configDirectory`, or by default in Mitome's config directory (`$MITOME_HOME`, else `$XDG_CONFIG_HOME/mitome`, with `APPDATA`/`HOME` fallbacks). When an application overrides it, pass the same directory to the Provider, for example `codex({ configDirectory })`.
