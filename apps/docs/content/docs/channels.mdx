A [Channel](/docs/concepts#host) is a Host that connects an external surface to the Agent. `@mitome/channels` ships first-party Channels, each on its own subpath; `@mitome/channels/http` is a generic HTTP Channel for an application or consumer client that has no messaging platform in between. [`mitome serve`](/docs/cli#serving-channels) runs it; the [Hosts](/docs/hosts#kind-channel) page describes the contract it implements.

```sh
npm install @mitome/sdk @mitome/channels
```

## Declare it

```ts title="index.ts"
import { defineMitome, fileTranscripts } from "@mitome/sdk";
import { fileRoutes } from "@mitome/core";
import { bearer, http } from "@mitome/channels/http";
import { agent } from "./agent";

const token = process.env.API_TOKEN;
if (token === undefined) throw new Error("API_TOKEN is required");

export default defineMitome({
  agent,
  transcripts: fileTranscripts(),
  hosts: [
    http({
      auth: bearer({ [token]: "owner" }),
      routes: fileRoutes(),
    }),
  ],
});
```

`http()` takes these options and returns a `kind: "channel"` Host exposing `handle` only:

| Option               | Meaning                                                                                                                                                                                                |
| -------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `auth`               | An `Authenticator`: `(request) => Promise<string \| undefined>` resolving the **principal** the request acts as. `bearer({ token: principal })` is the built-in one; write your own for anything else. |
| `routes`             | The [Route](/docs/hosts#routes) store: `fileRoutes()` survives restarts, `memoryRoutes()` does not.                                                                                                    |
| `approvals?`         | `"deny"` (default) or `"interactive"`; see [Approvals](#approvals).                                                                                                                                    |
| `approvalTimeoutMs?` | How long an `"interactive"` Approval may wait for a decision before it is denied. Defaults to five minutes.                                                                                            |
| `name?`              | The Channel name, unique in the Mitome Definition; `mitome serve` mounts the Channel under `/<name>`. Defaults to `"http"`.                                                                            |

Then run it:

```sh
mitome serve            # Serving Channel "http" at http://localhost:3000/http
```

## Run a Turn

```
POST /<name>/conversations/:id/turns
Authorization: Bearer <token>
Content-Type: application/json

{ "message": "Hello", "model": "openai/gpt-5.4-mini" }
```

`message` is the user Message. `model` is optional and selects a [qualified Model id](/docs/concepts#model) for this Turn only. The response is `200 text/event-stream`; read it with `curl -N` so nothing is buffered:

```sh
curl -N \
  -H "Authorization: Bearer $API_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"message":"What can you do?"}' \
  http://localhost:3000/http/conversations/demo/turns
```

```
event: model-output
data: {"v":1,"turnId":"6f1c…","event":{"type":"model-output","text":"I can "}}

event: model-output
data: {"v":1,"turnId":"6f1c…","event":{"type":"model-output","text":"help with…"}}

event: response-complete
data: {"v":1,"turnId":"6f1c…","event":{"type":"response-complete","finishReason":"stop","usage":{…}}}
```

Send the next Message to the same `:id` and the conversation resumes where it left off: the Channel looks the Route `(name, principal, id)` up, loads that Transcript, and seeds the Session with it. An `:id` the Channel has not seen starts fresh. The id is chosen by the client and is **not** authorization: two principals using the same id get two separate Routes, and one principal can never read another's conversation by guessing an id.

Authentication runs before anything else. A missing, malformed, or unknown bearer token is answered `401` before the Route store or a Provider is touched.

### The SSE envelope

Every frame has an `event:` line naming the event type and a `data:` line carrying one JSON `TurnFrame`:

```ts
interface TurnFrame {
  v: 1; // envelope version
  turnId: string; // minted per request; Approval decisions name it
  event: WireTurnEvent;
}
```

`WireTurnEvent` follows the public [`TurnEvent`](/docs/reference/api/core#turnevent) vocabulary, serialized:

| `event.type`        | Fields                                                           |
| ------------------- | ---------------------------------------------------------------- |
| `model-output`      | `text`                                                           |
| `reasoning`         | `text`                                                           |
| `tool-call`         | `id`, `name`, `params`                                           |
| `tool-result`       | `id`, `name`, `result`, `isFailure`                              |
| `approval-required` | `approvalId`, `toolCallId`, `name`, `params`, `requirement`      |
| `response-complete` | `finishReason?`, `usage?`; the last frame of a successful Turn   |
| `error`             | `message`; the last frame of a Turn that failed after it started |

Tool `params` and `result` values that are not JSON arrive as `null`. `response-complete` is written only after the Transcript was saved **and** the Route advanced, so once a client has seen it the next request will resume this Turn.

### Status codes

Before the stream starts, a failure is an ordinary status:

| Status | When                                                                                                |
| ------ | --------------------------------------------------------------------------------------------------- |
| `400`  | The body is not JSON, has no string `message`, or has a `model` that is not `provider/model`.       |
| `401`  | Unauthenticated.                                                                                    |
| `404`  | Unknown path, or the Approval endpoint when `approvals` is not `"interactive"`.                     |
| `405`  | A method other than `POST` on a known path.                                                         |
| `409`  | A Turn is already running on this Route; wait for it to end, or interrupt it by disconnecting.      |
| `413`  | The body exceeds 1 MiB.                                                                             |
| `500`  | The Route store, the Transcript store, or Session creation failed; the body is a fixed description. |

After the stream started, the status is never changed. A Turn that fails mid-way ends its stream with one `error` frame whose `message` is a fixed description (`Turn failed`, `Session busy`, `Session released`, or `Transcript store failed`); the Turn's own error text never crosses the wire, because the caller is a client rather than the operator.

Closing the connection interrupts the Turn: the Session closes, its Route is released, and any pending Approval of that Turn is forgotten. A Turn interrupted before its Transcript was saved is not committed.

## Approvals

The Channel resolves the [Approvals](/docs/approvals#who-approves-by-default) Core asks it for, and only those: a Tool call that is unflagged, or that the Agent's `approvals.allow` covers, runs without ever reaching the Channel.

By default every pending Approval is denied with a stable reason the Model sees:

```
Approval denied: the http Channel "http" does not resolve Approvals (set approvals: "interactive" or list the Tool under approvals.allow)
```

There is no channel auto-approve option. To run unattended, say so once in the Agent Definition with `approvals: { allow: [...] }`.

### `approvals: "interactive"`

With `approvals: "interactive"`, an `approval-required` frame leaves the Turn paused and the client decides:

```
POST /<name>/turns/:turnId/approvals/:approvalId
Authorization: Bearer <token>
Content-Type: application/json

{ "decision": "approve" }
{ "decision": "deny", "reason": "Not on production." }
```

Both ids come from the frame. The endpoint answers `204` and the Turn continues; the SSE stream then carries the `tool-result`. `reason` is optional on a denial and defaults to `Approval denied by the user.`

The decision is authenticated like any other request, and the caller's principal must be the principal of the Turn that is waiting; another principal that knows both ids gets `403`. An id the Channel is not waiting on, whether unknown, already decided, timed out, or belonging to a Turn that ended, gets `404`, and a decision never re-executes a Tool. Because this endpoint must reach a Turn that is currently holding its Route, it does not take the per-Route Turn lock.

An Approval nobody answers within `approvalTimeoutMs` (default five minutes) is denied with a stable timeout reason. Pending Approvals live in the process for the lifetime of their Turn only: a disconnect or a restart forgets them.

## Not promised

The HTTP Channel deliberately does not offer, and `v: 1` of the envelope does not imply:

- **Retries.** A failed Turn is reported once; the client decides whether to send the Message again.
- **Resumable SSE.** There is no `Last-Event-ID`; a dropped connection interrupts the Turn.
- **Durable pending Approvals.** They are forgotten when the Turn ends or the process restarts.
- **OpenAI API compatibility.** The paths and payloads are Mitome's own.
