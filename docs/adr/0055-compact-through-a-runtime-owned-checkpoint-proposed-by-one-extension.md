# Compact through a runtime-owned Checkpoint proposed by one Extension

Compaction is a projection, not a rewrite. Preserve every committed Message and derive the Model Prompt from the selected Branch's applicable Checkpoint: Instructions, the summary framed as a user Message, then the retained Messages. `history()` and the Transcript stay complete for their defined scope, so a Checkpoint can be discarded and recomputed with another Model or summarizer; rewriting Messages in place was rejected because it is one-way.

[ADR-0056](0056-separate-history-compaction-and-execution-recovery.md) requires branch-aware Compaction and separate execution recovery. The Checkpoint's retained boundary and applicability must be tied to compatible ancestry. The persistence design must settle their representation and the scope of `history()`/Transcript before #168 fixes a public shape: `{ summary, keepFrom }` with one numeric offset on a linear Transcript is not yet a tree-aware contract. A selected Branch cannot inherit a summary of its discarded future; carrying abandoned work requires an explicit Branch summary.

Extensions own policy; Core owns the transaction. One new Hook, `compact`, runs once per Step before `preStep` and once per manual `Session.compact()`. It receives facts, the canonical Messages, the current Checkpoint, the selected Model's ids and `contextWindow`, the last Step's Provider-reported usage, and a scoped `generate` function that runs a no-tools completion through the Session's Model resolver, and returns a new Checkpoint or nothing. Core validates the Checkpoint (non-empty summary, an in-range retained boundary with compatible ancestry, and no split between a Tool call and its results), applies it to later Steps of the Turn, and commits it to conversational history only with the Turn's Transcript save. A failed, interrupted, or unsaved Turn leaves the committed Checkpoint in place; separate Execution state must preserve any staged Checkpoint needed to recover unfinished work. Core never triggers Compaction itself and holds no threshold or retention settings. `preStep` keeps ADR-0024's ephemeral contract; `compact` is a fourth Hook verb, propose, because it returns durable state rather than a transformed Prompt. Exactly one Extension in an Agent Definition may declare `compact`; more is an `AgentDefinitionError`, as with duplicate Tool names. A failing `compact` fails the Turn like every other Hook; an Extension that prefers to degrade catches and returns nothing.

`contextWindow` has one source: Provider metadata, generated from models.dev for known catalogs and declared per Model on the Provider factory for compatible endpoints. A Compaction-side override was rejected as a second truth for the same fact. Core clears the usage it passes when a Checkpoint applies, when the selected Model changes, and at Session start, so Extensions never see pre-Compaction usage as current.

The default lives in `@mitome/sdk/extensions` as `compaction({ trigger, boundary, summarize })`, a factory over three function-typed seams with exported defaults (`tokenThreshold`, `keepRecent`, `summarizeWithModel`). Authors replace a seam, compose the defaults into their own `compact` Hook, or write against Core directly, the same ladder `instructions`, `instructionFiles`, and a hand-written `{ instructions }` already form. A dependency graph for Extensions to build on a Core compaction Extension was rejected again (ADR-0041, ADR-0053): the contract is the Hook's types, and customization is passing a function, not depending on a value. Summaries are not gated by the Model that produced them; a smaller-window Model simply sees the same text and the Extension compacts again if needed.

This reverses ADR-0040's deferral of Compaction. The persistence design will choose how Checkpoints are represented alongside the History tree and Execution state before #168 changes Transcript schema version 1; ADR-0036's migration chain starts at first publish. Manual Compaction fails with `SessionBusyError` while a Turn is active rather than interrupting it. Overflow recovery, a compact-and-retry after a context-limit error, is deferred until Core has a portable overflow classification; when added it must run at most once per Turn and never replay a Step that executed Tools.

## Consequences

- `Session.compact()` returns the Checkpoint; token estimates stay with the Extension that made them.
- A mid-Turn Checkpoint may retain only in-flight assistant and tool Messages, leaving the current user request inside the summary; carrying the task forward is the summarizer's job, and Core validates structure only.
- A retained boundary must remain valid on the selected Branch. Branching before Compaction or onto divergent ancestry must select an applicable earlier Checkpoint or omit it; indexing alone cannot establish summary provenance.
- Test independent Compaction on two Branches, navigation before/after Compaction, explicit Branch summaries, and recovery with staged Compaction without advancing committed history.
