# Separate history, Compaction, and execution recovery

Mitome will support embedded applications and user-composed local coding Agents with built-in durability, rather than make each Host implement recovery. [ADR-0057](0057-use-effect-native-functions-and-optional-host-composition.md) selects function-first authoring and optional Host composition; the [library plan](../plans/effect-native-library.md) preserves the full replacement gates. Turn-only persistence loses too much unfinished work; Step-only persistence cannot distinguish an interrupted Tool from an external operation that completed before its result was recorded. Preserve completed-Step progress and Tool intent/outcomes separately from completed-Turn conversational commits. This is an accepted direction, not an implemented guarantee; storage, schemas, and public APIs still require design. Delivery is tracked in [roadmap #174](https://github.com/chenxin-yan/mitome/issues/174), with the shared persistence contract in [#170](https://github.com/chenxin-yan/mitome/issues/170).

## Recovery contract

The first durable runtime has one coordinating process and supports restart recovery, not concurrent distributed workers. Recover safe work automatically, reuse recorded Tool outcomes, and retry unknown outcomes only under explicit replay safety and application/upstream idempotency. An unknown unsafe outcome pauses for reconciliation. An unresolved commit or unsafe external-effect outcome also blocks new Turn execution on the affected Transcript across Sessions/Routes until recovery or an explicit reconciliation decision permits admission. Browsing remains available; independent Transcripts may continue when storage is healthy. This is history/execution fencing, not workspace isolation. Allowing new work while the earlier outcome remained unresolved was rejected. Approval authorizes execution; it does not make replay safe or guarantee exactly-once external effects.

An explicitly configured Tool reconciler may establish an uncertain external operation's outcome without repeating the operation. Failed or inconclusive lookup leaves work blocked for authorized intervention; the absence of a reconciler never licenses a retry. This allows evidence-based automatic reconciliation rather than requiring human intervention for every uncertain outcome.

An authorized operator may explicitly abandon work while acknowledging an unknown external effect, but only once history-commit state is known and the previous execution can no longer publish history. Preserve the unknown external outcome and abandonment decision; do not publish unfinished conversation, claim rollback, or silently replay work. This avoids permanently blocking a Transcript when an external service cannot establish its outcome, without treating an uncertain history commit as safely abandoned. Exact reconciliation authority, operations and evidence validation remain to specify.

Durable Hosts may accept ordinary custom Agent programs without a resumable continuation. Acceptance durably records work and known outcomes; it does not make arbitrary code replayable. After a crash, automatically resume only compatible library-owned continuations or explicitly resumable application work. Unsupported or incompatible running custom work pauses for reconciliation instead of being reinvoked. Requiring every durably hosted custom program to declare recoverability up front was rejected to preserve function-first authoring without silently weakening replay safety. Exact continuation declarations and compatibility checks remain design work.

Accepted work outlives its client connection. Disconnect detaches observation; explicit cancellation stops further execution cooperatively and cannot undo completed effects. Pending Approvals and cancellation decisions survive restart. For durably hosted work, acknowledge cancellation once the request is durably saved, explicitly as requested rather than stopped. Execution settlement and already-committed or unresolved outcomes are reported separately; neither the acknowledgement nor cancellation implies that external effects were undone. Waiting for all execution cleanup before acknowledging the saved request was rejected because a stuck Tool or finalizer could prevent any response. Embedded applications may still opt out of durable storage; persistence remains explicitly composed rather than inferred by a Host.

Durable submissions require a stable submission key scoped to the authenticated Principal within the application. The same key and request resolve to the original accepted work; reuse with a different request is rejected, not treated as new work. First-party Hosts manage keys transparently, while HTTP callers supply and reuse them. Supported recovery retains the original Turn identity; a duplicate submission never authorizes arbitrary program reinvocation. Optional keys were rejected because a lost acceptance response would otherwise make safe retries conditional on caller opt-in. Keep the minimal acceptance receipts needed to recognize old keys without automatic expiry, independently of bulky result retention. A deleted result must not make an old submission new work. This deliberately permits receipt storage to grow with accepted work; a finite deduplication window that could repeat external effects was rejected. The first replacement exposes no receipt-forgetting or namespace-retirement API. Explicit application-result payload deletion remains supported, but must retain the receipt and comparison data needed to reject changed requests and recognize retries. Forgetting receipts while continuing to accept their old keys would weaken the selected guarantee; a destructive namespace lifecycle would require a separate future decision. Exact request comparison and identity formats remain to specify.

New submissions must identify their expected execution Branch/history position. Reject a stale expectation rather than silently running against different context; the client refreshes and explicitly resubmits. After authorization and matching the submission key/request, an already-accepted retry still returns its original work: freshness checks govern new admission, not previously accepted work. Exact position/version representation and request comparison remain open.

The first durable cancellation or success-commit decision wins. A saved cancellation decision prevents conversation commit; a completed commit yields already committed rather than cancellation success. Request arrival order or an in-memory flag is not the authority. Cancellation acknowledgement may wait behind an in-flight save; an uncertain write outcome must be reconciled before claiming which decision won. This governs durable controls, not native caller interruption, which is not itself a saved cancellation decision. Advisory cancellation that can be acknowledged and then lose to a later commit was rejected.

For work promising a durable application result, encode that result before conversation commit and atomically save committed conversation with its authoritative success outcome/result. Encoding failure prevents conversation commit without undoing external effects. History-first/result-later publication was rejected because it introduces an avoidable partially published success state. Ordinary embedding retains arbitrary application result types without automatic serialization. Persist a safe generic application-failure classification by default; richer application error data requires an explicit author-supplied codec. Do not automatically serialize arbitrary errors, stacks or defects. Direct callers retain their exact live Effect error types. Mandatory application-error codecs were rejected to avoid requiring extra authoring ceremony for every durably hosted program. Retain completed application-result payloads until explicit deletion; there is no automatic expiry initially. Deletion preserves the minimal acceptance/outcome receipt so the original work remains identifiable and its result is reported unavailable, never regenerated by rerunning work. Storage grows until the owner cleans it up. Exact wire classifications, retrieval/deletion operations and bounded recovery attempts remain to specify.

Acknowledged durable state must survive both process failure and machine failure (OS crash or power loss) on supported local storage that honors required flushes. This includes accepted work and saved Approval/cancellation decisions; do not acknowledge durable acceptance before the necessary transaction and synchronization complete. Process-only recovery was rejected because losing an acknowledged control decision after power loss would violate the intended contract. This is a target guarantee to prove, not a claim about the current file store or scratch proofs, and does not cover broken hardware or filesystem corruption. Backend, synchronization policy, and evidence remain part of #170; process-kill tests alone do not prove power-loss durability.

First-party durable storage initially requires supported local disk; network-mounted/shared database files and remote database services are outside the initial support contract. Remote clients may still access the owning application through HTTP. This bounds filesystem and coordination assumptions while preserving machine-crash durability; it does not select SQLite, a journal mode, or a physical schema. First-party durability must be available to both Node and Bun applications; the library plan owns the selected runtime/platform targets and their verification gates.

## Queued work and execution controls

Follow-ups are separate accepted Turns, not implicit retries or steering. Failure or cancellation of preceding work pauses pending follow-ups rather than silently continuing or deleting them; resumption is explicit and remains subject to settlement, shared-position validation and unresolved-outcome fences. Steering that reaches no further Model safe point receives a recorded not-applied outcome, not an automatic new Turn. These choices avoid changing execution intent or creating new work from input meant for a finished invocation. The canonical plan and #171 own the concrete queue/control protocol.

Step/Tool-count limits stop further controlled work beyond the bound, but a custom Agent may catch the limit and deliberately complete with structurally valid staged conversation. The default loop still fails on exhaustion. This preserves ordinary Effect recovery without overriding cancellation, deadlines or uncertainty fences. When configured, a persisted execution deadline starts at execution entry rather than enqueue time and includes Approval waits and process downtime; restart does not reset it. Expiry requests cooperative termination and cannot guarantee immediate cleanup or hard wall-clock enforcement.

## History contract

A History tree preserves Message ancestry and alternate Branches. Selecting an earlier user Message positions a new continuation before it and restores its text for editing; selecting another Message continues after it only where the resulting Model Prompt is structurally valid. Branch selection reconstructs context, never executes historical Tools. Workspace files and external effects remain unchanged.

A Transcript has one persisted Execution position shared by every Session and Route referring to it. Attached TUIs and other views browse independently, but execution Branch selection changes that shared position; stale submissions reject instead of silently following the new Branch. Independent execution positions require distinct Transcripts. Separate persisted Session/Route heads were rejected to avoid conflicting selection/recovery owners within one Transcript. Browsing is allowed during a Turn, but switching the execution Branch requires an idle Session after execution has settled; acknowledging a cancellation request does not imply settlement or release admission. Unresolved outcomes remain subject to the reconciliation fence. There is at most one active Turn per Session and at most one across all Sessions/Routes sharing a Transcript, including different Branches. Reject competing execution admission rather than implicitly waiting; explicit follow-up queues are a separate capability. Independent Transcripts may execute concurrently, including parallel child work. This strengthens the per-Session rule so loading another Session cannot bypass history ownership. Multiple TUI views are not multiple execution owners: [ADR-0050](0050-discriminate-hosts-by-kind.md) selects explicit connection to a running application and its shared Session, without automatic local-owner discovery. Optional Branch summaries carry information from an abandoned Branch into the new one only on explicit request; they are off by default. Compaction alone never imports another Branch's future.

## Distinct responsibilities

- The Transcript owns the canonical committed History tree and its associated Checkpoints. A selected Branch's linear conversation is a projection, not a second authoritative record. Keeping Transcript as a path and introducing another durable tree owner was rejected to avoid competing identities and sources of truth. This selects the domain representation, not physical storage, loading strategy or a public schema.
- A Checkpoint is Compaction state, not an execution recovery record. It applies only to compatible ancestry. Preserve all Messages and derive the Model Prompt from the selected Branch and its applicable Checkpoint.
- Execution state preserves unfinished work, Tool outcomes, Approvals, and cancellation independently of Transcript commits. Recovery must restore any staged Compaction state used by that work without publishing it as a completed Turn. Custom Agents may inspect earlier Tool outcomes after a later failure through the shared read-only execution-query contract, also used for recovery/operator views. Preserve original application errors rather than wrapping them or adding resumable Step handles; reading evidence never authorizes replay or clears uncertainty. Exact query identity, access, lifetime and payload contracts remain in #170.
- Delivery state lets a client retrieve accepted work and its results after reconnecting. A replayable client stream, if provided, is not itself authority to rerun effects.

These responsibilities need not use separate databases or packages. Choose physical storage and APIs in the persistence design, including stable identities, branch-valid boundaries, summary provenance, crash-consistent writes, and recovery when Agent programs or Tool implementations change. Keep `Step` as one model generation; keep `Checkpoint` reserved for Compaction.

This revises ADR-0036's exclusion of mid-Turn recovery and Approval restoration, while retaining the distinction between committed history and unfinished execution. It retains ADR-0040's explicit composition rule and amends ADR-0055's linear Checkpoint assumption. The current process-bound SDK and HTTP disconnect behavior remain the implemented contracts until their replacement is delivered.

## Evidence

Pi v0.85.1 uses parent-linked entries and a selected leaf for ordinary coding Session navigation; its context projection picks Compaction from that path. This supports the history design, not a claim that its ordinary SessionManager recovers in-flight execution. See the pinned [navigation](https://github.com/earendil-works/pi-mono/blob/d981de1229ef899957bbe968bc8dcda02a21f477/packages/coding-agent/src/core/agent-session.ts#L3236-L3286) and [context projection](https://github.com/earendil-works/pi-mono/blob/d981de1229ef899957bbe968bc8dcda02a21f477/packages/coding-agent/src/core/session-manager.ts#L334-L469) implementations. Mitome requires valid branch boundaries rather than adopting implicit synthetic Tool-result repair.
