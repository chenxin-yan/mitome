## What the format does and does not specify

| Area                        | Primary-source finding                                                                                                                                                                                            | Mitome implication                                                                                                                |
| --------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------- |
| Required format             | A Skill directory contains `SKILL.md`, YAML frontmatter and Markdown body. Required `name` is 1–64 characters with naming/directory constraints; required `description` is nonempty and at most 1,024 characters. | Validate the chosen format explicitly. Merely reading Markdown is not compatibility.                                              |
| Optional fields             | `license`, `compatibility` (1–500 characters when present), string-to-string `metadata`, and experimental `allowed-tools`.                                                                                        | Environment descriptions do not install dependencies; metadata versions do not prove recovery compatibility.                      |
| Disclosure                  | The spec describes metadata first, body on activation, resources as needed. The main-body token/line sizes are recommendations.                                                                                   | Avoid eager Model-context insertion of every Skill. Do not mislabel local parser/resource limits as normative format maxima.      |
| Discovery                   | The client guide recommends user/project directories and deterministic precedence; the format itself does not prescribe search roots.                                                                             | The owner chose explicit configuration, not ambient home/project discovery. No project-over-user override is implicit.            |
| Resources                   | Relative references use the Skill root; scripts, references and assets are optional organizational conventions.                                                                                                   | Resolve relative resources against the selected Skill, not ambient cwd. Reading/activation is not script execution or permission. |
| Authority                   | Experimental `allowed-tools` has varying client support and no Mitome policy, argument-binding or recovery mapping.                                                                                               | No automatic grant, Approval decision, Tool exposure or replay permission follows from Skill content.                             |
| Recovery / filesystem trust | The cited format does not establish immutable directory snapshots, symlink containment, crash recovery or a sandbox.                                                                                              | Specify these separately; do not infer them from format compatibility.                                                            |

## Differences that prevent blindly copying the reference code

- The name prose says “unicode lowercase alphanumeric” while also giving ASCII ranges. The validator normalizes names and directory names with NFKC and uses Python lowercase/alphanumeric checks. That is a concrete interpretation, not an unambiguous ASCII-only requirement.
- The specification names `SKILL.md`; the reference parser additionally accepts `skill.md`.
- The reference validator rejects unknown top-level fields. The specification does not explicitly prescribe that rejection, while the guide discusses vendor-specific flags.
- The guide explicitly recommends lenient name/directory handling and even possible malformed-YAML repair. Those are compatibility recommendations, not strict format requirements. The owner selected strict validation with diagnostics instead.
- The reference validator permits an empty `compatibility` string despite the specification's stated minimum. Its metadata parser also stringifies metadata keys/values. Reusing it would not by itself prove strict validation of the published field constraints.

The owner subsequently selected **retaining unknown top-level fields inertly, with warnings**, while strictly validating standard fields. This deliberately differs from the reference validator; it does not implement vendor controls or coerce unknown values into the standard string-valued `metadata` map. The owner has now selected the [Mitome compatibility profile](../plans/effect-native-library.md#selected-compatibility-profile): NFC Unicode names without repair, strict UTF-8/YAML handling, explicitly designated Skill directories or shallow collections, and finite configurable byte/count limits. This is a client profile, not a claim that the specification mandates its normalization, YAML subset or limits. Parser/platform fixtures and enforcement qualification remain outstanding. No parser dependency is selected or approved for installation.

## Fit with the selected architecture

[ADR-0057](../adr/0057-use-effect-native-functions-and-optional-host-composition.md#configuration-over-convention) records the owner's clarification: keep Core minimal and choose configuration over convention. Optional ordinary Effect operations can load, validate and select a catalog; applications explicitly compose Model exposure through native Tools/Toolkits. Native Layers provide actual infrastructure where needed, not a new Extension registry or mandatory plugin lifecycle. With no configured Skills there is no implicit scan or catalog. An optional scanner receives explicit roots; duplicate names require explicit selection rather than silent precedence.

The existing [`instructionFiles`](../../packages/sdk/src/extensions/instruction-files.ts) accepts an explicit `import.meta.url` base for relative paths, validates host-absolute paths without a base, and discovers bare instruction filenames from git root to cwd. Reuse the explicit-base behavior from completed #167 where appropriate. Its instruction discovery is not Skill-directory discovery, and its obsolete Extension return carrier is not the new architecture.

Skill files remain instruction input, not trusted executable imports. Catalog declaration, activation, resource reads and execution are separate. Strictly invalid Skills are disabled with actionable diagnostics, without silently repairing input or honoring unsupported vendor controls. Arbitrary imported application JavaScript remains trusted/unsandboxed, as elsewhere in Mitome.

The owner selected Turn-scoped activation with active instruction content protected through Compaction and supported recovery; explicit catalog loading pins `SKILL.md`, and managed resource reads pin files on first use per Turn. Unread resources can still change: no complete or atomic bundle snapshot is promised. The managed reader stays within the selected Skill root, including symlink-target checks, without granting additional file authority. Unknown fields are retained inertly with warnings. The [canonical lifecycle contract](../plans/effect-native-library.md#selected-activation-and-content-policy) owns these policies, explicit refresh and remaining qualification gates.

The pinned client guide recommends keeping Skills effective for a whole Session, protecting content from Compaction, deduplicating activation and allowlisting Skill directories. It also explicitly allows either retaining bodies at discovery or re-reading them on activation. These are client-design recommendations, not normative format requirements. Mitome selects a shorter activation lifetime, pinned consulted content and no automatic directory allowlisting. Protecting an active body in the Model Prompt is distinct from retaining resource bytes as recovery evidence; ordinary committed history may still contain Skill text after activation ends.

## Required future checks

- No configured roots means no ambient discovery, including in CLI/TUI.
- Invalid standard metadata disables the Skill; unknown top-level fields remain inert and produce visible warnings, never vendor behavior or authority. A vendor boolean cannot hide or expose a Skill.
- NFC `résumé` and `中文` names work with matching directories; decomposed metadata names, uppercase names, edge/consecutive hyphens and overlength names reject without repair. Directory-only canonical decomposition is compared as specified; compatibility lookalikes never silently alias through NFKC. Character counts use code points, not UTF-16 code units.
- Valid UTF-8 with a leading BOM and LF/CRLF parses; invalid UTF-8, lowercase-only filenames, non-line frontmatter separators, duplicate/nested non-string keys, aliases/anchors/merge keys and custom tags reject. Scalar types remain truthful: numeric `metadata.version` rejects instead of becoming text. Empty bodies and literal `---` within body text are preserved.
- An explicit Skill directory and an explicit shallow collection have distinct behavior. Collection scanning never descends into nested directories or follows discovered links outside its root; missing `SKILL.md` on a directly selected Skill reports an error. Overlap, duplicate names, relative-resource resolution and symlink escape are deterministic and bounded.
- Each byte/count limit passes exactly at its boundary and fails visibly above it; rejected candidates and consumed bytes cannot bypass aggregate limits. Over-limit reload leaves the prior catalog usable, not partially replaced. Growing files, special files, concurrent first reads and symlink/replacement races cannot defeat the selected bounds or containment. Static path-prefix/realpath checks alone do not qualify race-safe containment.
- Discovery/diagnostic reads never execute scripts or expose undeclared Tools.
- Editing `SKILL.md` after catalog load cannot change that version's activation body; repeated resource reads/recovery retain captured content, while a previously unread resource may reflect a later edit.
- Compaction preserves an active Skill's actual instructions for the Turn without splitting Tool exchanges; a later Turn does not inherit active status merely because Skill text remains in history.
- Refresh affects subsequent bindings, not an already-bound Turn; missing recovery content does not trigger a changed-file fallback.

These are acceptance obligations, not executed tests. No production files, upstream sources, compiler or dependencies were changed by this research.
