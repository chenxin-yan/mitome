## Current implementation versus accepted direction

At inspected HEAD `c343410`, `@mitome/sdk` is Promise-facing (`defineAgent`, `defineExtension`, `withSession`), `@mitome/sdk/effect` is a facade over the same Agent Definition/Extension contracts, and Hosts expose Promise operations. The execution engine already uses Effect; there must not be a second execution engine. Current HTTP execution is connection-owned and process-local; persisted Transcripts do not recover unfinished work. The accepted target below is **not shipped**. Removing obsolete prerelease guides and ADRs does not change those exports or establish durability.

No proposed Session/generation/Host signature in earlier discussions is an export commitment. API examples and reference pages return only with verified contracts and implementation. Existing source/tests remain evidence for migration, not the target authoring specification. There is no Promise compatibility surface to preserve in the redesign.

**Owner-selected clean cutover:** replace the prerelease APIs and implementation outright; do not add compatibility aliases, legacy readers/importers, dual writes or a second execution path. First-party persistence uses a separate, versioned storage location/namespace for the replacement. Leave existing on-disk Transcript files untouched; the new TUI does not promise to browse them, and missing new-store state must not silently fall back to them. A future explicit import is outside this replacement's requirements. This does not authorize deleting user data or changing production now. Port useful behavior and tests, not obsolete Definition/Extension/Promise contracts. No required #174 capability is deferred by dropping backward compatibility. This initial prerelease cutover is not a receipt-forgetting facility for the replacement store: later incompatible state must fail explicitly, not silently initialize an empty store and make accepted keys executable again.

## Accepted direction

- **Function-first library.** An Agent program is an ordinary typed Effect-returning function with an ambient Session dependency. Preserve arbitrary application result, error, and requirement types. No mandatory agent wrapper, per-agent service token, class, or Layer-valued agent. Native Layers acquire infrastructure; native Tool, Toolkit, Schema, and model types describe model work. Providing a service does not expose a Tool to the Model. Reusable features are ordinary modules, functions, Tools, and Layers, not mandatory Extensions or a custom DI graph.
- **Explicit ownership.** Allocate each Session explicitly in a Scope, never through implicit/global state or a memoized shared Session Layer. Ordinary nested calls share the supplied Session. The app/Host owns a whole-function Turn: stage conversational Messages across any number of generations, commit once after successful program completion and durable save when persistence is enabled. Program, interruption, or cleanup failure before commit leaves committed history unchanged; failed/interrupted acknowledgement after commit is not rollback, and uncertain storage outcomes require reconciliation. Already completed external effects are not rolled back. Each invocation supplies a Turn Scope: resources and scoped children acquired inside it settle/clean up before commit; child work whose success or result matters is explicitly joined. Native Effect semantics apply: unjoined child failures, including child cleanup defects, do not automatically fail the Turn; its own scope cleanup defects do. Acquire shared infrastructure outside the Turn; returning a resource handle does not extend its lifetime. Reject concurrent Turns on the same Session and use after release.
- **One composable execution path.** Provide independently usable primitives and a default loop built from the same controlled operations that custom loops use. Run as an Effect yielding its typed result; bounded passive progress observation is separate from authoritative Approval, cancellation, acceptance, and commit outcomes. Observer failure, slowness, or disconnect must not decide execution lifetime.
- **Optional Host composition.** Retain the `defineMitome` concept as explicit declarative composition, not `new Mitome`, required agent packaging, or a second agent API. Its future fields/generics remain open. The CLI loads one explicitly selected typed composition; no magic named-export discovery. A documented single default export is permissible, not yet a finalized loading protocol. Declaration does not acquire Sessions, models, terminals, or listeners. Embedded users can import their program and infrastructure without importing Host/TUI code and explicitly provide interaction/consent when needed.
- **User-owned configuration.** Provider/model selection, Session defaults, and persistence belong to user composition. One Provider descriptor set supplies discovery/auth/catalog information and runtime provisioning. Discovery/authentication must work without opening a Session or acquiring authenticated model clients. Preserve qualified Model ids, catalog-as-hints, known context-window metadata, explicit instruction-file bases, ordered static Instructions, and distinct ephemeral per-Step shaping.
- **Local durable storage first.** First-party durability initially requires supported local disk, not network-mounted database files or remote database services ([ADR-0056](../adr/0056-separate-history-compaction-and-execution-recovery.md#recovery-contract)). Remote clients may use HTTP. Backend, exact supported runtime versions and synchronization policy remain undecided.
- **Runtime/platform support targets.** Support direct library use and first-party durable storage on Node 24 or newer and Bun; CLI/TUI execution remains Bun-based. Verify exact minimum patch versions rather than claiming every release meets the storage contract. Retain all eight existing binary targets: macOS and Windows x64/arm64, plus Linux x64/arm64 on both glibc and musl. Require native validation of supported runtime/platform combinations; cross-compilation alone is not support evidence. The npm CLI's Node launcher floor is separate from Agent execution and persistence requirements.
- **Two deliverables.** Deliver the library and CLI/TUI, not a separate coding-agent product. The owner's coding Agent is a library composition and acceptance scenario. Initial usable Host scope is TUI plus mountable HTTP; a Channel includes HTTP and later messaging surfaces. Design the gateway seam now; Discord/Telegram implementations remain deferred, including #138. Hosts share execution and persistence semantics, not separate loops or implicit per-Host stores.
- **Full replacement, not a smaller release.** Durable recovery, Message-level History trees, Compaction, Skills, steering/follow-up queues/budgets, subagents, and controls all remain #174 release gates. A process-local TUI/HTTP slice is an internal proof only. Embedded callers may deliberately opt out of durable storage; that does not waive the durable replacement gate.

## Ownership and safety boundaries

| Boundary                    | Responsibility                                                                                                                      |
| --------------------------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| Agent program               | Behavior, explicit Tool selection, typed application result; no transport startup or hidden Session allocation.                     |
| Infrastructure              | Native scoped acquisition of model implementations, handlers, stores, and shared services; no automatic model-visible registration. |
| Session/Turn                | Staging, whole-invocation commit, controlled model/Tool execution, busy/released checks, and authoritative controls.                |
| Shared routing              | Authorized conversation mapping and logical-Route admission before independent Session/history acquisition.                         |
| Host                        | Transport authentication, input/output mapping, consent presentation, and transport lifecycle.                                      |
| Application/optional runner | Shared infrastructure Scope, explicit Session allocation, Host selection, execution ownership, and shutdown policy.                 |

Authenticate and authorize before Route/history/model access. Default routing separates Channel, authenticated Principal, and conversation; sharing across principals or Hosts needs explicit authorization. Approval, cancellation, and result retrieval enforce ownership: knowing an id is not authority. Reject competing execution on a logical Route as well as overlapping Turns on a live Session or shared Transcript, even across different Branches. Independent Transcripts remain concurrent; parallel child work needs its own Transcript. An in-memory lock proves only single-process exclusion. Multiple TUIs explicitly connect through authenticated HTTP to one running application and share its live Session and execution Branch, while browsing history independently. Execution-Branch changes require an idle Session after actual settlement, not merely a cancellation-request acknowledgement. Connected TUI exit detaches that client; stopping the application closes its owned Session. Retain idle application-owned Sessions until an authorized explicit close or application shutdown; do not automatically evict them after the last client disconnects. Admission/resource limits remain separate. Competing standalone owners are rejected, not silently attached. No automatic local-owner discovery/background startup on resume is required initially (ADR-0050).

Author policy remains fail-closed ([ADR-0051](../adr/0051-let-the-agent-author-decide-tool-approvals.md)): Tools flag risk, reusable policy can tighten, the Agent author decides, and Hosts resolve permitted asks. Missing consent denies; policy failures never silently permit execution. Native upstream approval parts are not an authenticated decision service. In inspected Effect rc.108/rc.117, the native approval check recovers typed failures as no approval needed; this is not proof that defects are swallowed or that an unauthorized execution was reproduced. The controlled execution design must establish its own fail-closed authority (see the [native boundary audit](../research/native-generation-boundary.md)). Arbitrary user Effects are not sandboxed.

Hosted accepted work belongs to the application execution scope, not the client connection; direct embedding follows caller scope. Disconnect detaches observation, authorized explicit cancellation stops further work cooperatively, and completed external effects remain. For durably hosted work, acknowledge cancellation after saving the request, explicitly as requested rather than stopped; report execution settlement and committed/uncertain outcomes separately (ADR-0056). Bound/coalesce progress and signal gaps; keep authoritative outcomes separately retrievable. A failed Route update, event append, or terminal acknowledgement after commit must not masquerade as rollback or trigger reinvocation.

Build shared infrastructure once per application Scope; allocate fresh Sessions deliberately. Preserve startup unwind, individual serving-Host failure reporting while healthy Hosts remain, no implicit restart loop, and shutdown after stopping admission. The standalone CLI has a configurable best-effort grace period, defaulting to five seconds, then exits nonzero on expiry if the event loop responds; external supervision owns hard wall-clock enforcement. Embedded code never terminates its host process or treats pending cleanup as completed ([ADR-0050](../adr/0050-discriminate-hosts-by-kind.md)). Shared infrastructure failure is not an isolated transport failure. HTTP remains mountable without CLI registration; publishing arbitrary typed results requires explicit Schema/encoding, not automatic serialization. Interactive, request-handling, and long-lived gateway lifetimes must remain distinct.

## Authoring and composition contract — working draft

This translates the verified execution mechanics into caller responsibilities. It is a proposed interface contract, not selected export names or production implementation. Bounded heterogeneous registration and optional composition have now passed independent source/log review and parent compiler/runtime verification; the [evidence and limits](../research/native-generation-boundary.md#generic-registration-and-optional-composition-probes) remain separate from the public interface. A subsequent [typed loading and real Session/Turn connection](../research/native-generation-boundary.md#typed-loading-through-the-real-sessionturn-boundary) also passes within a single-invocation application lifetime. Long-lived Host composition, final public fields and the remaining execution/durability contracts are still pending.

### Ordinary programs and owned execution

An Agent program remains an ordinary function from application input to `Effect<A, E, R>`. Its inferred R may include application, Model, Tool and managed-execution requirements; do not force every program into a fixed Session-only environment or erase its errors/results. Application input is not automatically a conversational Message, and application result A is not automatically an assistant Message. The program or its explicit Host mapping decides that conversion.

| Caller responsibility                                                      | Library responsibility                                                                                                                                                  |
| -------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Provide native infrastructure Layers in an enclosing application lifetime. | Preserve acquisition errors/requirements and keep Session/Turn work within that lifetime; do not discover dependencies by executing Agent code.                         |
| Explicitly allocate a fresh scoped Session.                                | Own its live state, admission and close/drain behavior; never obtain freshness by building a memoized Session Layer.                                                    |
| Invoke the ordinary program through the whole-function Turn operation.     | Supply invocation context and Turn Scope, reject overlap/released use, stage conversation, drain required work/cleanup and publish only after successful save.          |
| Compose ordinary nested Effect functions.                                  | Keep them in the existing Session/Turn unless the caller explicitly allocates and invokes a different Session.                                                          |
| Stage intended native Messages within the Turn.                            | Keep committed history distinct from staged Model Prompt projection; do not let observation publish partial conversation.                                               |
| Select Tools and Model work explicitly.                                    | Apply the controlled generation/Tool path, serial resolution, validation, policy and execution ownership rather than inheriting native automatic approval as authority. |
| Observe progress, optionally.                                              | Run independently of observation; bound/drop passive updates and keep authoritative controls/outcomes separate.                                                         |

The proven generic Turn operation preserves A, adds boundary errors to E and removes only the execution services it actually supplies from R. Handler acquisition Scope and invocation Scope are not interchangeable: infrastructure can be captured at registration, while resources acquired against the invocation's Scope belong to the Turn. Internal ownership/drain mechanics must not become ceremony repeated in every Agent.

### Controlled primitives and the default loop

Prefer one controlled Step operation as the reusable unit for both custom programs and the default loop. It constructs the Model Prompt from the selected committed projection plus staged Messages, performs one generation, handles its eligible local Tool calls serially under policy, and stages the completed conversational contributions. This does not introduce another meaning of Turn: several Steps can still belong to one function invocation.

The author receives completed operation data using native response/result types, not a stream whose consumption determines execution. Source inspection confirms a public native response constructor; the smaller candidate is to retain the original native response alongside this operation's separately resolved local Tool-result parts. Preserve provider metadata and distinguish the original response's results from later local execution rather than implying its getters include both. A [bounded type/runtime proof](../research/native-generation-boundary.md#step-result-and-once-acquired-application-qualification) now checks the candidate container: original `LanguageModel.GenerateTextResponse<Tools, "encoded">` plus `ReadonlyArray<Response.ToolResultParts<Tools>>`. Use encoded parameter mode for disabled native resolution, preserve heterogeneous result discrimination, and do not imply native content is deeply immutable. A localized internal correlation assertion bridges validated native HandlerResult output; it does not erase Effect E/R. The owner-selected classified complete/incomplete result below extends this completed-response candidate; its exact native generic signature and option names still require qualification. Exposing a separate generate/resolve protocol with resumable handles is not required merely to implement the default loop. Add such a public split only for a demonstrated author use case with explicit ownership and once-only semantics.

The default loop repeats that same Step operation; it must not add a second dispatcher, policy path or commit point. **Selected incomplete-output policy:** when the Provider explicitly reports an incomplete response, the default loop fails rather than silently returning successful partial completion. Do not execute local Tools from that response or automatically commit partial history. A custom Agent may deliberately handle the partial result, subject to valid conversation structure and existing fences; this does not undo remote effects or authorize replay. **Selected missing-metadata policy:** accept an otherwise successful, normally validated provider response when finish metadata is absent; absence alone is not a failure. Explicit incomplete/error output still follows the failure policy. **Selected retry default:** add no implicit Mitome model-request retries beyond configured native Provider behavior. Explicit safe retry/recovery must retain its accounting and never blindly repeat a whole Turn or a Step that may have executed Tools. Native/provider-internal retries are not thereby disabled or proved safe; qualify and account for their behavior at the actual request boundary. Exact failure/result representation, other completion/continuation rules and retry/budget accounting remain to specify. Raw native Model/Tool Effects remain available to application code, but bypassing the controlled operations does not acquire Mitome's staging, policy or recovery guarantees; user code is not sandboxed.

The [source checkpoint](../research/native-generation-boundary.md#remaining-step-and-tool-variant-contracts-source-checkpoint) separates facts from the next decisions: native finish-metadata absence differs from explicitly incomplete output; raw JSON-Schema Tools are not natively validated; provider definition origin does not establish execution locality. The owner selected explicit handling of incomplete output, JSON-Schema interoperability and bounded pre-request grants for remote capabilities; those policies are recorded here without reopening ordinary authoring or local serial execution. Native pending approval artifacts can trigger handler execution before the disabled generated-call resolution branch, so the controlled Prompt/approval protocol cannot rely on that flag alone. Such artifacts are not Mitome authority; imported or restored data must not dispatch outside controlled ownership. A focused approval-input check now reproduces this path and tests a narrow rejection candidate; full controlled-Step integration remains open. Do not classify it as an upstream defect or patch Toolkit merely from this finding.

#### Controlled Step execution contract — candidate

The following makes the working draft concrete without selecting public export names. It is not a new execution engine or an assertion that every row is already proved.

| Boundary         | Candidate contract                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| ---------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Entry            | Require the current managed Turn; do not allocate a Session or start a nested Turn. Use its current execution position, selected Model, applicable Checkpoint and staged Messages.                                                                                                                                                                                                                                                                                                                              |
| Options          | Accept the participating Tool selection, native Tool-choice intent and explicit invocation-local Model provision. Prompt construction, automatic resolution, serial local execution, ownership and commit are controlled invariants, not caller switches. Provider-specific generation configuration remains native.                                                                                                                                                                                            |
| Before request   | Check admission/cancellation/fences and applicable budgets. Validate bindings and any Provider capability grants before exposing remote capabilities. A `toolChoice` value is not authority and does not replace output validation.                                                                                                                                                                                                                                                                             |
| Model output     | Retain the complete original native response. Classify explicit incomplete/error output before local dispatch; do not execute its local Tool calls. Accept missing finish metadata after normal validation. Use the content-based completion rules below, not the first-finish getter; provider-specific continuation still requires qualification.                                                                                                                                                             |
| Local resolution | Resolve only calls matching selected, handler-bearing local bindings, serially, through the existing once-decoded policy/intent/owned-drain path. Do not fall through to ambient handlers or infer remote permission from a response marker. Native error-mode failures propagate; return-mode failures remain result data, not permission or a fence-clearing signal.                                                                                                                                          |
| Staging/result   | On normal completion, stage the structurally complete conversation contribution using native projection and return the original response plus native parts for this operation's separately resolved local results. Preliminary results remain progress, not completed conversation. A returned Step result is not a Turn commit receipt.                                                                                                                                                                        |
| Failure/recovery | Preserve typed application failures, defects and interruption. Do not publish a successful Step result or malformed partial Tool group. Completed external work and durable execution evidence are not rolled back; an Agent's explicit recovery still must respect conversation validity and unresolved-outcome fences. Expose partial outcomes through the selected shared read-only execution-query contract, not a new error wrapper or resumable Step handle; exact schema/access rules remain to specify. |

The default loop uses these same operations and returns the final completed Step rather than a second transcript accumulator; custom Agents can retain intermediate values normally. The following technical rules refine the candidate without claiming provider conformance or end-to-end dispatch/staging verification:

| Response state                                                       | Controlled/default-loop behavior                                                                                                                                                                                                                               |
| -------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Absent finish or `stop`, otherwise valid                             | Accept. Continue after actual eligible local resolutions (including native return-mode failure data); otherwise finish only when no unresolved provider obligation remains.                                                                                    |
| `tool-calls` with eligible unresolved local calls                    | Resolve serially, then continue using the completed results. This is a new Step, not retry of the previous request.                                                                                                                                            |
| `tool-calls` without eligible local work                             | Reject malformed/missing call groups. For provider-only work, require a qualified terminal/continuation rule; do not repeat merely because a call or finish reason exists.                                                                                     |
| `pause`                                                              | Native regards this as complete for its resolver, but that proves neither finality nor safe continuation. Without a qualified provider rule, fail unsupported continuation before local dispatch; do not silently treat it as success or replay authorization. |
| Explicit `length`, `content-filter`, `error`, `other`, `unknown`     | Default loop fails before local dispatch or automatic partial staging. Explicit unknown differs from absent metadata. Custom handling retains the selected incomplete-output policy.                                                                           |
| Error part, malformed/contradictory output or failed provider Effect | Do not project away the problem and report success. Preserve native Effect failures/defects/interruption; validate response content and call/result groups before dispatch.                                                                                    |

Inspect the whole native content: `finishReason` conflates absent metadata with explicit unknown and reports only the first finish. Native projection is not call-group validation. Managed streaming cannot start local handlers before complete classification while promising no local execution from incomplete output. Native generation can itself retry an incremental request without incremental state on `InvalidRequestError`; the selected no-extra-Mitome-retry default does not guarantee one physical request. Such retries remain an authorization/accounting qualification gate.

**Selected classified Step result:** a successfully returned, explicitly incomplete Model response is a distinct incomplete value, not a library error that custom Agents must catch. Preserve the original native response for inspection; perform no local dispatch or automatic staging for that variant. A complete value carries the native response and separately resolved local result parts described above. These are proposed semantic variants, not final exported names or a deeply immutable response wrapper. The default loop converts the incomplete variant into its own failure policy; a custom Agent can inspect it and deliberately choose valid next work, subject to all existing fences and conversation rules. Actual Provider/Tool Effect failures, defects and interruption remain failures with their original types, not incomplete values. Malformed/contradictory protocol data and unsupported continuation do not become successful complete results. A completed-only container is therefore insufficient; the earlier proof qualifies only the complete payload, not this final result union or full dispatch/staging integration.

**Selected partial-outcome access:** custom Agents may inspect earlier Tool outcomes after a later Tool fails through the shared read-only execution-query contract owned by #170. Reuse that execution evidence for live inspection and recovery/operator views instead of adding a second trace store, error wrapper or resumable generate/resolve API. Queries must distinguish recorded results, missing/deleted payloads, in-flight work and unknown outcomes; a known handler failure does not prove no external effect occurred. Reading evidence cannot clear a fence, establish settlement or authorize replay. The derived [shared query contract](#shared-read-only-execution-queries--candidate) specifies selection, snapshot/lifetime, authorization/redaction, payload availability and non-durable behavior; these scratch fixtures prove none of it.

**Managed approval input boundary:** authoritative Mitome Approvals are control/execution state, not permissions reconstructed from conversational parts. The generic managed-generation candidate rejects raw native approval request/response parts before invoking LanguageModel; it does not silently strip them or interpret their IDs as authorization. A dedicated provider-deferral integration must prove its native request mapping and authority binding before accepting those artifacts, without accidentally entering the local native pre-resolution path. This is boundary validation in Mitome's own proposed protocol, not a Toolkit patch or a claim that native APIs forbid their normal approval workflow. A [focused scratch counterexample/check](../research/native-generation-boundary.md#pending-approval-boundary-check) covers this narrow rejection rule; full Step/Session/recovery integration is still pending.

### Tool registration: keep library plumbing out of author declarations

Participating registration is the supported candidate: authors supply native Tools plus ordinary handler maps/builders, while controlled operations own authorization, intent ordering and cleanup. Arbitrary prebuilt handler Layers cannot be promised transparent interception. The integrated proof's explicit gate schemas/dependencies are evidence, not the preferred public authoring requirement.

Prefer unchanged Tool declarations first. The independently reviewed [bounded authoring probe](../research/native-generation-boundary.md#unchanged-declaration-authoring-probe) now demonstrates internal gate provision with native error mapping, exact concrete types and fail-closed controls, without modifying author Tool schemas or dependencies. Native handler types already permit `AiError` independently of an author's failure schema. This candidate maps **only library-owned typed gate failures** into that existing error channel. It must not remap user handler errors, turn defects into permission, expose private failure details, or treat return-mode failure data as successful authorization. **Selected failure reporting:** use the native `AiError` channel with safe library-generated denial text, without promising a dedicated machine-readable denial case. That text is informative, not a control protocol. This does not merge denial, defects, interruption or uncertain durable writes into one execution state; return-mode failure data never clears a fence or authorizes further work.

**Proposed registration contract:** accept a native Toolkit plus an ordinary handler map or Effect builder. Acquire the builder once within the enclosing infrastructure lifetime, retain its typed construction E/R, and snapshot its managed bindings. Retain native definitions for Model exposure; keep prepared handlers private and expose only controlled execution. Fresh operation-local registration supplies the gate without schema transformation. Preserve native capture-before-builder semantics and invocation-context precedence; decoder/encoder and application services remain truthful invocation requirements. Do not silently subtract requirements merely because a captured context may contain them.

Check visible names, IDs and exact handler keys before Mitome merges/registers them, within the selected execution environment rather than a global registry. Reject missing/ambiguous bindings instead of falling through to ambient handlers. The heterogeneous proof covers those checks, captured/ambient/prebuilt handler replacement, binding snapshots and authority expiry during asynchronous authorization/intent. It also retains the counterexample that duplicate names already discarded inside an author's native `Toolkit.make` cannot be recovered. Native Tool values remain trusted, not hardened against arbitrary mutation.

The tested generic operation uses an explicit native result/error/service return annotation; removing it fails the exact error assertion. Neither unrestricted inference nor automatic lifetime safety follows. The bundle and authority plumbing are internal candidates, not approved exports. Host-executed Effect-Schema Tools are the tested selection; dynamic/provider subtypes can be carried unchanged, but their execution policy still needs a contract. Boolean authority checks do not prove durable fencing. Subsequent tests integrate the candidate with the actual Session/Turn kernel, including held-cleanup cancellation; they retain its lifetime/detached-work qualifications. The connecting source build also requires the guard's optional `toolCallId` constraint to allow explicit `undefined`, matching native HandlerContext under exact optional-property checking. The earlier registrar evidence remains frozen; this is a candidate typing correction, not an upstream or runtime patch.

### Selected Tool-variant policies

**Raw JSON-Schema interoperability:** validate supported JSON Schema dialects without silently changing their meaning; reject unsupported schemas before use. Advertising a schema to a Provider does not validate local input. Preserve ordinary Effect-Schema Tool declarations and the once-prepared-argument gate. A raw-schema adapter must bind its advertised schema, validator and prepared arguments consistently; do not add duplicate author schemas or quietly fall back to `Schema.Unknown`. The native importer's documented subset/value differences are insufficient as a transparent interoperability promise. Exact dialects, reference/pattern/resource limits and validator selection remain technical work; this decision authorizes no dependency installation or claim of universal schema support.

**Remote capabilities:** [ADR-0051](../adr/0051-let-the-agent-author-decide-tool-approvals.md) now permits explicit bounded Provider capability grants before the Model request. They are not per-call Approvals or a blanket inference from Tool selection. If stricter policy requires exact-argument consent, require genuine provider-side deferral or reject before dispatch. A local handler cannot retroactively authorize remote work, and a response's `providerExecuted` flag is not permission. Distinguish provider-defined local handlers, which use the local gate, from remotely executed actions, which need the pre-request boundary. Do not claim constraints the Provider/request boundary cannot enforce. Concrete binding/expiry/ownership, durable recording, returned-result validation and unknown-outcome recovery remain to specify; a capability grant alone never permits replay.

### Optional composition, not another Agent abstraction

Direct embedding supplies infrastructure, allocates a Session and invokes its ordinary program without a Host/CLI import or mandatory result codec. Optional `defineMitome` composition adds the data and explicit bindings needed to load and expose that same program: Provider discovery/authentication, Model selection, Session defaults, infrastructure and selected Hosts. It does not replace the program with a service token or introduce a second execution engine.

Separate declaration/discovery, resource acquisition, Session allocation and invocation. Discovery/authentication commands must not invoke the Agent or acquire a live Session/model merely to learn configuration. Importing a module still executes trusted JavaScript; this is not a sandbox or a promise that arbitrary module initialization is inert. Dynamic validation can check the supported exported shape and native values, not reconstruct erased TypeScript A/E/R or infer that a Layer satisfies unknown requirements.

One Provider descriptor set supplies non-secret discovery/catalog/authentication data and lazy provisioning. Preserve provisioning Layer construction E and unmet R rather than assuming every Provider is closed/infallible; native `Model.make` accepts construction error `never`, so it must not erase a fallible custom provisioner's error channel. Acquire shared infrastructure before allocating fresh Sessions, not by folding Sessions into a memoized shared Layer.

**Proposed composition contract:** retain the original program function and native infrastructure in a small declarative record, with the single Provider descriptor set, optional defaults and selected Hosts. Discovery projects metadata only. Selection resolves a qualified Provider/native Model ID without calling its provisioning factory; acquisition calls only the selected factory. Defaults apply only when selection is omitted, never as recovery from malformed explicit selection. Split qualified IDs at the first slash; catalog entries remain hints, not an allowed-model enumeration. A lexical native Model or explicitly selected Provider override applies to its invocation without mutating application defaults.

The composition probe preserves arbitrary in-process results, fallible infrastructure/Provider E/R, and concrete static closure using ordinary provision. Dynamic selections honestly retain possible requirement/error unions. Fresh allocation and Host startup are stand-ins in the initial composition probe. Subsequent actual-kernel and loaded-entry tests establish the bounded Session/Turn connection, not a serving-Host lifecycle. Runtime shape validation must leave erased function requirements unknown; a structurally valid non-Effect-returning function is an intentional counterexample, not something a loader can turn into a type guarantee.

Hosted input decoding, conversation mapping and promised result encoding must be explicit and independently typed at actual serialized boundaries. An attached TUI crosses HTTP; a standalone in-process TUI does not by itself require another author wire codec. A direct application's arbitrary return value is not permission to serialize it through HTTP, persistence or terminal output. Durable publication follows the existing encode-before-commit rule. Concrete static provision and a typed producer/loading boundary are tested. Exact optional fields, module export/version/error protocol, long-lived Host entry and transport mappings remain to specify rather than copy from the current Promise/Definition implementation.

#### Typed producer and trusted loading

Keep the original Agent function and its exact A/E/R in the statically typed composition. Alongside it, expose an explicitly application-closed execution entry for dynamic loading. An optional identity helper or record constraint checks the producer's entry without widening its concrete record type. Application, Provider, infrastructure and any codec requirements must actually be provided; only explicitly known host-supplied requirements may remain. The bounded protocol proves Scope-only closure, not an arbitrary runtime service registry.

At dynamic import, validate the supported export shape and accept the trusted producer's promised entry signature at one documented boundary. Do not cast the raw Agent or an arbitrary Layer into a closed program. Dynamic result/error types are unknown and not automatically serializable. Check that invoking the entry returns a native Effect, while preserving application failures and defects. This check cannot recover R: a valid-looking module returning a native Effect with a missing service remains a deliberate counterexample that defects at invocation. Arbitrary module initialization, dishonest JavaScript and incorrect declarations remain outside the type guarantee; neither a version marker nor shape validation is authentication or sandboxing.

The connected fixture now runs that loaded entry through actual Session allocation, generic native registration and whole-function Turn execution. It checks real conversation save, no-commit denial and cancellation that waits for required cleanup before Session/infrastructure release. It owns infrastructure for one invocation. A long-lived Host must instead acquire shared infrastructure once for its application lifetime, retain explicit Session ownership across requests and invoke the same Turn path; do not turn the single-call fixture into per-request application startup. No Promise facade or second execution engine is needed.

### Long-lived application and Host contract — candidate

Keep the original typed program independently importable. For optional dynamic loading, replace the single-invocation proof's per-call acquisition with one producer-closed **application acquisition Effect** that yields bound Host capabilities for its enclosing lifetime. This is a proposed replacement shape, not a second mandatory entry alongside the scratch `execute`, an Agent service token or a new runtime. A producer must actually close application requirements for acquisition and subsequent callbacks; acquiring a function inside a provided Effect does not itself provide that function's later execution. Preserve invocation/Turn Scope precedence rather than accidentally substituting the captured application Scope. Known caller/platform requirements stay explicit. At the dynamic boundary A/E remain unknown and closure remains a trusted producer promise, not a runtime shape-check result.

The acquired value is an ordinary scoped record of bound capabilities, not a public service registry. It must not escape resource release as a supposedly live application. Direct embedding still uses the ordinary program, native provision, fresh Session and Turn primitives without this record. Model selection remains lazy: shared infrastructure is acquired once, not every Provider client eagerly; invocation overrides do not mutate defaults.

Retain distinct native capabilities: an interactive operation for terminal interaction, a request-handling operation for mountable HTTP, and scoped acquisition/running behavior for long-lived gateways. The [once-acquired application proof](../research/native-generation-boundary.md#step-result-and-once-acquired-application-qualification) now verifies a concrete producer record with genuinely closed execution callbacks, explicit real Sessions, repeated whole-Turn saves, idle retention, request detachment after admission and shutdown blocked by required cleanup. Observation correctly retains caller Scope. Merely acquiring a function under native provision demonstrably does not close its later R. Its process-local launch ticket is not an acceptance receipt; admission failure may arrive through its join. Exact generic acquisition/capability signatures, dynamic loading of this new record, readiness/error protocol, transport/result mappings, admission races and authenticated controls remain unqualified. The earlier loaded proof remains single-invocation evidence, not a dynamically loaded long-lived Host. The current CLI's startup unwind/isolated serving failures and lazy TUI entry are migration references; current HTTP's per-request Session and consumer backpressure driving execution are behavior to replace, not target guarantees.

## Derived contract draft

This is a technical proposal derived from the accepted policies and [Pi source comparison](../research/pi-reference-architecture.md), not new shipped exports or a claim of tested persistence. Keep ordinary author functions and native Effect provision; the following records/operations belong behind that boundary. Exact declarations still require compiler/runtime proofs and the final specification review.

### Identity and history position

| Identity             | Proposed meaning and lifetime                                                                                                                                                                           |
| -------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Transcript           | Stable owner of committed Message ancestry and Checkpoints. Reopening does not create another Transcript; an explicit independent fork does.                                                            |
| Live Session         | Scoped runtime allocation, not a serialized process object. Attached clients share its owner; a restart allocates new resources for the existing Transcript.                                            |
| Submission key       | Opaque retry identity scoped to application and authenticated Principal; lookup only, not comparison data or authority. Only a winning acceptance binds it; rejection binds nothing.                    |
| Acceptance receipt   | Immutable record named by one scoped key: command kind, comparison version/data, Turn and pinned target. Never expired, deleted or reassigned; result deletion leaves it intact.                        |
| Turn                 | Opaque identity allocated only in the winning acceptance, one-to-one with its receipt; kept across recovery and lookup. Retries and losing concurrent attempts allocate no visible Turn.                |
| Step                 | One controlled generation, identified before the provider request. An allowed retry is another attempt at the same logical Step, not permission to repeat the whole program.                            |
| Tool invocation      | One logical Tool effect, with a runtime-owned identity independent of the provider's Tool-call id. Preserve it, recorded arguments and any upstream idempotency binding across permitted retries.       |
| Message / Checkpoint | Assign identity when durably recording staged content and preserve it when that content commits. Checkpoint provenance refers to actual ancestry/boundaries, not array offsets in a mutable projection. |
| Approval             | Identifies one pending decision bound to the exact Tool invocation and prepared arguments. Repeating a decision cannot authorize a new invocation or changed arguments.                                 |
| Payload reference    | Stable reference to one recorded encoded payload and its representation/codec version. Survives deletion with deleted availability; knowing it grants no read access.                                   |

A Turn identity is never derived from its key, Route or provider data. Other durable acceptance kinds (#171 enqueue, #173 child launch) reuse this receipt shape and key-first operation; their retry-identity derivation and anchoring stay with those issues. A non-durable Turn has a live identity but no durable receipt; no key is recognized after its owner's release. How direct embedding with persistence enabled scopes submission keys is not selected here.

Prefer opaque identifiers and parent links, not paths, timestamps or provider-generated IDs as ownership authority. Resolve Message/Checkpoint references within their owning Transcript; knowing an identifier never grants cross-Transcript access. **Selected position ownership:** one persisted Execution position belongs to the Transcript, shared by every Session/Route referring to it. Session allocation does not create an independent selected head. Independent execution positions require distinct Transcripts; a viewer's browsing cursor is not a persisted execution selection.

The proposed position token contains the Transcript identity, selected Message head (or empty root) and a monotonically increasing **Transcript revision**. History publication, execution-position changes and committed Checkpoint changes increment that revision, including changes away from and back to the same head; browsing and progress do not. Checking only a head would miss that change-away/change-back race. Branch selection requires confirmed settlement and no blocking fence, validates a structurally valid conversation boundary, then compares and advances the revision atomically. Opening/reusing a Session must not silently execute against a newer shared position than the caller accepted. Queue anchoring remains #171's separate decision.

A **Turn execution revision** changes when its authoritative execution/control/payload-availability records change. It is not the Transcript revision, progress-event sequence, wall clock or evidence of current liveness. Durable writer authority also needs a separate incarnation/fencing token: a new live Session ID alone cannot exclude stale publishers. Exact identifier and revision encodings and the owner-exclusion mechanism remain verification gates; these distinctions do not require a new public service registry.

### Shared read-only execution queries — candidate

Queries are ordinary Effect operations over the same execution records used by recovery, not consumption of a progress stream or a second execution engine. The operation and outcome names below describe semantics, not approved exports; whether an outcome travels in the success or error channel is a later signature decision, but every listed outcome must stay distinguishable. Read operations never run an Agent, Tool, Model request, reconciler or application-input decoder merely to retrieve known work.

| Operation                 | Input                                                                                                                         | Returned facts                                                                                                                                                                                                                                                                                                 | Other outcomes                                                                                                                                                                                                                         |
| ------------------------- | ----------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Resolve a submission      | Caller authority and an application/Principal-scoped key; no request body, so it also serves a request that cannot be resent. | Receipt identity, command kind, comparison version, Turn identity and pinned target Transcript, after Route changes, result deletion or application-code changes. Comparison data and input are payload-class content, not receipt metadata.                                                                   | `absent`: key confirmed unbound in that view, never a reservation. `not-accessible`: the key is bound but its stored target is no longer accessible; it still never becomes new work. `unavailable`: inconclusive read, never absence. |
| Read a Turn snapshot      | Caller authority and a Turn identity (directly or from a resolved receipt).                                                   | One confirmed view: accepted base (or #171 anchor), configuration references, execution revision, recorded phase, saved controls and pending Approvals, known or unknown outcome, per-payload availability and blocking uncertainty. Owner activity and durability are labelled separately from durable facts. | `not-accessible` (for foreign work, indistinguishable from nonexistence), `unavailable`, `released`.                                                                                                                                   |
| Inspect Step/Tool records | Caller authority, Turn identity, the execution revision from a snapshot, a cursor and a configured finite page bound.         | An ordered page of runtime identities within that Turn; provider call IDs as correlation only; recorded request attempts, responses, intents, outcome classifications and payload references, in the record states below.                                                                                      | `revision-changed` (restart from a fresh snapshot), `not-accessible`, `unavailable`, `released`.                                                                                                                                       |
| Read a payload            | Payload authority and a payload reference.                                                                                    | `available`: the stored encoded representation with its representation/codec version, without invoking author codecs.                                                                                                                                                                                          | `not-produced`, `not-promised`, `deleted`, `unsupported-representation` (this library cannot interpret the stored record), `unavailable` (read failure, never evidence of deletion or absence), `not-accessible`, `released`.          |
| Decode a payload          | Payload authority plus an explicitly supplied compatible codec.                                                               | The typed value, with that codec's truthful E/R.                                                                                                                                                                                                                                                               | Codec/version incompatibility is a decode failure, not deletion; an undecodable payload is never authority to repeat work.                                                                                                             |

Step/Tool record states stay distinct; none of them clears a fence, establishes settlement or authorizes replay:

| Recorded facts                                                | Reported as                                                                                                         |
| ------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------- |
| Tool intent, no outcome, owner confirmed active               | In flight.                                                                                                          |
| Tool intent, no outcome, owner not active or activity unknown | Outcome unknown: potentially executed, even if the process may have died before dispatch.                           |
| Recorded unknown outcome                                      | Outcome unknown, with any recorded reconciliation evidence reference.                                               |
| Recorded success                                              | Success; payload availability reported separately.                                                                  |
| Recorded failure                                              | Failure with its safe classification and any codec-produced payload; not evidence that no external effect occurred. |
| Classified incomplete, unencodable or uncertain generation    | Not a completed Step; no successful partial Step is fabricated.                                                     |

**Authority and redaction.** Authenticate remote callers before lookup and authorize against the stored work/resource, not only the Route's current mapping. Keys, receipts, IDs, payload references and cursors grant no access, and responses must not disclose whether foreign work exists. Status, payload and control authority are separate: reading a Turn's status grants neither sensitive payload access (including comparison input) nor any control. In-process, the running Turn's owned execution context may read that Turn's own records, which is the selected partial-outcome use; other in-process reads need explicit read authority from the application, whose form is not selected. Ordinary embedding does not require a Channel Principal. Apply the same authorization/redaction policy to direct queries and Host projections; do not expose arbitrary stored secrets, stacks or defects through a convenient diagnostic endpoint.

**Snapshot and revision.** A response describes one confirmed store view, not a new cancellation decision combined with an older claim that none exists. Durable facts are monotone: a later view never loses a receipt, entry intent, saved control or known outcome, and a deleted payload never becomes available again. Transcript position and Turn execution revision are returned separately. Cursors are bound to Turn and execution revision; a changed view reports `revision-changed` rather than silently claiming one coherent snapshot. Do not hold a database transaction open for a client or pin unlimited history for abandoned cursors. Payload reads report current availability, which may postdate the snapshot. Owner activity is an observation, not a durable fact: report "not active" only where current writer authority establishes it (owner exclusion is still a verification gate), otherwise unknown.

**Live errors versus durable payloads.** A live typed error or result reaches its caller only through the native E/A of the operation that produced it. Queries return recorded facts (safe outcome classifications and payload references), never the live object or a wrapper around it, in both durable and non-durable modes. A recorded failure carries a safe generic classification by default; richer error data exists only when an explicit codec produced a versioned payload, and defects/interruption are classifications only. A query's own failure (unreadable, corrupt or unsupported record) is reported as that query's `unavailable`/`unsupported-representation` outcome, never written into or confused with the Turn's outcome, deletion or absence.

**Lifetime and non-durable mode.** Durable reads remain independent of the original Session, its services and the program's current availability, and survive restart. Receipts and comparison data are retained indefinitely; application-result payloads until explicit deletion. With persistence opted out, the same operations and outcomes read the live owner's in-memory records while that lifetime exists, each response marked non-durable, with an application result `not-promised` unless a declared codec encoded it. They promise no restart retrieval. After owner release, queries report `released` rather than reconstructing records or reacquiring an Agent, and a handle or cursor does not extend that lifetime. Payload/codec revisions are part of the record, not a generic cast to the caller's current Tool type.

**Reads never authorize.** No query launches, enters or resumes work, dispatches a Model, Tool or reconciler, decides an Approval, saves cancellation, clears or narrows a fence, establishes settlement or reserves a key or capacity. `absent`, `deleted`, `not-produced`, a recorded failure or a missing live owner is never permission to run work again. Every later mutation revalidates under current writer authority; a snapshot revision may be supplied as a conditional control's expected revision, which conflicts when stale, never as proof of state.

Not selected here: identifier, key, revision and comparison encodings or value domains; page and payload size bounds; retention of diagnostic payloads other than application results (it must not remove records that recovery or fences depend on); the form of in-process read authority; and the failure classification vocabulary.

### Durable submission protocol

1. Authenticate the Principal and authorize the application operation before exposing Route/history/model state. Parse the bounded, versioned transport envelope; credentials are not submission identity.
2. Look up the application/Principal-scoped key. For existing work, check current access to its stored target and compare the original request: matching work returns its original receipt/outcome; a changed request conflicts. Do not re-resolve a mutable Route/default, run the current application-input decoder or reapply history freshness before returning known work. Unsupported comparison data never becomes permission to accept a new Turn; key-only retrieval still has a separate query contract.
3. After an initial key miss, prepare new work: resolve/authorize its target and program, validate input, capture immutable invocation/configuration references without serializing live services/secrets, and check position, ownership, fences and budgets. This miss is provisional. Before returning a new-work preflight rejection, authoritatively recheck the key: an existing authorized matching receipt takes precedence; a changed request conflicts; only confirmed absence at that rejection's decision point permits the new-work rejection. An unavailable/inconclusive recheck cannot claim absence. This does not bypass current access checks to stored work or convert caller interruption into acceptance. Trusted author validation/provisioning is not sandboxed or universally side-effect-free.
4. In one short atomic acceptance operation, check the key **first**, returning authorized matching work or a conflict before applying new-admission checks. Only while the key remains absent, recheck the authoritative target/position, ownership, exclusion/fences and admission accounting, then persist the receipt, Turn identity, comparison data and required execution references. Concurrent equal-key submissions return one original acceptance; changed requests conflict. A different key while the Transcript/Route is occupied rejects rather than creating an implicit queue. No library-controlled program/Model/Tool dispatch follows an ambiguous acceptance write.
5. Start under application ownership only after confirmed acceptance, independent of the connection. Returning an existing receipt does not launch work. The application owner must exclusively claim entry through a conditional durable transition under current writer authority, still-owned admission, no saved cancellation, compatible binding and applicable budget checks; only its confirmed winner may invoke the program. Persist this **program-entry intent** before calling the Agent function itself, not merely before running the Effect it returns. Absent entry intent permits initial invocation only after confirmed state/ownership and compatible binding checks. Present entry intent means user code _may_ have run, including a crash just before the actual call: an arbitrary program must not be automatically reinvoked. Synchronous code in a function returning an Effect is why deferring only its returned Effect is insufficient.

**Versioned submission comparison.** The receipt stores its comparison record once: command kind, comparison version and comparison data. The comparison version names the library-owned rules for which fields are included and how structured values compare. It is independent of application decoders, physical storage format and transport-envelope version.

- **Included:** command kind (immediate execution versus enqueue), the submitted target reference as sent rather than the Transcript a Route currently resolves to, the expected position token, application input as structured wire data rather than a value produced by the current decoder, explicit Model selection and its presence, and other execution-affecting options.
- **Excluded:** the key itself, the Principal (already its scope), credentials, tracing, connection IDs, observation preferences and resolved defaults. Resolved defaults and deletable result payloads are stored separately from comparison data.
- **Equality:** object member order is insignificant; array order, member presence and values are significant, so an omitted default differs from the same default supplied explicitly. The selected policy implies no other normalization (no Unicode normalization, case folding, trimming or default filling). Numeric-domain equality (for example `1` versus `1.0`, large integers), duplicate object members, canonical byte encoding and any digest or privacy scheme remain open; no custom hash protocol or dependency is selected. A digest-only representation would additionally need specified collision and privacy properties.
- **Evaluation:** compare a retry under the receipt's stored comparison version, never the library's current default. An unsupported stored version, unreadable or corrupt stored data, or a retry that cannot be mapped into that version is `incomparable`: an explicit error that is neither match, conflict nor permission for new work. Key-only resolution still returns the receipt. The first replacement exposes no receipt forgetting; comparison data survives result deletion and is never treated as an empty slot.

Submission outcomes:

| Outcome            | Decided when                                                                                                                                              | Consequence                                                                                                                                          |
| ------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- |
| New acceptance     | The key is absent inside the winning atomic acceptance and every new-admission check passes.                                                              | Receipt and Turn are written; invocation still requires the separate exclusive entry claim.                                                          |
| Existing work      | The key is bound, its stored target is accessible and the retry matches under the stored comparison version.                                              | Original receipt plus current snapshot facts. No freshness, occupancy, fence, capacity or new-work byte check applies; nothing launches or reserves. |
| Conflict           | The key is bound, its target is accessible and the comparison differs.                                                                                    | No new work under that key; new work needs a new key.                                                                                                |
| Incomparable       | As defined above.                                                                                                                                         | No acceptance or conflict claim; resolve by key.                                                                                                     |
| New-work rejection | Stale position, occupied Transcript/Route, fence, capacity or byte limit, or invalid input, decided only on confirmed key absence at that decision point. | Writes no receipt and binds no key; a later submission under that key is evaluated afresh.                                                           |
| Not accessible     | Authentication or authorization fails, or a bound key's stored target is no longer accessible.                                                            | Discloses nothing beyond the caller's own key scope and never becomes new work.                                                                      |
| Outcome unknown    | The key lookup is inconclusive or the acceptance write is unconfirmed.                                                                                    | No absence-dependent rejection and no entry; retry the identical request under the same key or resolve by key.                                       |

Exact rejection classifications and wire representations remain open.

Routes select a stable Transcript, not a fresh child Transcript after every Turn. An accepted receipt pins the actual target even if a Route later changes. A Route pointing at missing/corrupt authoritative history must not silently start fresh. Explicit new-Transcript/initial-Route creation can be part of atomic acceptance; its empty metadata is not staged conversational history. Route repair after a known commit does not rerun work or rewrite the accepted base. These replace the current `Routes` contract's per-Turn fork/advance and missing-target fallback, not merely wrap them.

### Authoritative writes and views

| Operation                                    | Required atomic relationship / ordering                                                                                                                                                                                                                                              |
| -------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Accept work                                  | Retry receipt and admission refer to the same Turn and execution base. No model or Tool execution before confirmed acceptance.                                                                                                                                                       |
| Begin a Step                                 | Persist its identity/attempt and budget accounting before dispatch; persist the complete response before executing its Tool calls. Partial stream progress is not a complete response.                                                                                               |
| Begin a Tool                                 | Validate and apply policy, durably record any Approval wait/decision, then record prepared intent before the external effect. Do not keep a database transaction open while awaiting a Model, Tool or human.                                                                         |
| Finish a Tool                                | Save its outcome before advancing controlled execution. Unknown outcome writes fence further controlled work; arbitrary user Effects remain unsandboxed.                                                                                                                             |
| Request cancellation                         | Serialize the durable decision against terminal success. Acknowledgement describes the saved request, not completed cleanup.                                                                                                                                                         |
| Publish success                              | After body success and Turn cleanup, check admission/cancellation ownership and absence of an unresolved-outcome fence, then atomically publish staged conversation/Compaction, history position and the promised success outcome/result. Encode promised results before this write. |
| Publish failure / cancellation / abandonment | Retain the receipt and known execution evidence without publishing unfinished conversation. Unknown history commit is not converted into a definite failure or abandonment.                                                                                                          |
| Repair delivery / routing                    | Read the authoritative outcome; repair or report delivery/Route failures without invoking the program again. A lost response cannot reverse a successful commit.                                                                                                                     |

Keep transactions short and related authoritative records in one transaction-capable store boundary; this does not choose physical tables or SQLite. Define domain-specific operations rather than expose a public transaction builder or general event-sourcing framework to Agent authors.

Status is a projection of durable execution/control records and current owner activity, not an independently authoritative second state machine:

- **Accepted:** receipt exists; program-entry intent has not been recorded.
- **Executing:** admitted execution is active; pending Approval can be shown separately.
- **Cancellation requested:** durable control exists; work may still be settling.
- **Paused:** supported continuation is unavailable/incompatible or reconciliation prevents progress. It is not success, failure or permission to replay.
- **Terminal:** known success, failure, cancellation or guarded abandonment; result deletion changes payload availability, not the outcome or retry identity.
- **Unavailable/unknown:** authoritative state cannot presently be established. Do not overwrite a potentially committed outcome with a guessed terminal status.

These are semantic distinctions, not finalized mutually exclusive wire discriminants. A known failed/cancelled Turn can still leave its Transcript fenced by an unresolved external effect; terminal execution alone does not clear that fence. A stored cancellation decision must remain effective after restart; observer gaps are repaired by authorized snapshots/status queries, not by treating replay of progress events as execution recovery.

### Logical persistence records — candidate

These are record responsibilities/constraints, not a selected SQL schema, backend interface or event-sourcing framework. They may share physical tables/storage. Existing `TranscriptStore.save/load/list/appendEvent` and `Routes.get/set/clear` lack these transactional semantics and are migration inputs, not implementations of them.

| ---------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Transcript             | Stable identity, shared selected Message head and monotone history revision. One admission owner across Sessions/Routes; selection cannot change beneath an admitted Turn. Committed history and Checkpoints remain distinct from staged execution.                                       |
| Message / Checkpoint   | Immutable identity within its Transcript, parent/ancestry references and versioned payload. Validate complete conversation boundaries and Checkpoint provenance before selection/publication; foreign-Transcript or discarded-future references cannot become the current projection.     |
| Submission receipt     | Unique application/Principal/key, immutable command kind/comparison version/data, accepted work identity and target. Normal execution versus enqueue is part of request identity. Keep receipt/comparison data after result deletion; an existing key is not reassigned.                  |
| Turn                   | Accepted base position and input/configuration references, execution revision, admission/entry claim, control decisions, outcome, payload availability and accounting. A live Session object or function is not serialized. Entry claim is conditional, not a timestamp proving code ran. |
| Step / request attempt | Stable Step identity and ordering within its Turn; separately recorded request attempts, input/steering references, complete response or uncertainty, and budget charges. A logical Step is not proof of one physical Provider request.                                                   |
| Tool invocation        | Runtime identity linked to Step and exact managed binding/preparation; provider call ID is correlation only. Persist intent before dispatch and outcome before advancing. Keep replay/idempotency/reconciliation information with the invocation, not inferred from current Tool names.   |
| Controls / queue       | Invocation-bound Approvals and Turn-bound cancellation/steering; ordered queued Turn references and predecessor/base anchoring per Transcript. Library-known credentials and live services belong to reacquired infrastructure, not invocation configuration snapshots. Application inputs/results may themselves be sensitive and require the declared storage/access policy; arbitrary payloads cannot be made safe by pretending to detect every secret. Persisted representation/codec compatibility and size limits must be explicit before the actual schema is selected. Incompatible or unencodable response data must not authorize local Tool dispatch; a recording failure after an external effect preserves the relevant uncertainty rather than manufacturing rollback.

### Durable controls and recovery eligibility — candidate

Every authoritative mutation must validate current writer authority and the target operation's immutable binding; snapshots and stale liveness observations cannot substitute for that check. Use domain operations at the store boundary, not a public general transaction builder. Backend-specific writer exclusion and crash-safe fencing remain unqualified; do not infer them from an in-memory lock, PID, timestamp or expired lease.

| Operation                            | Durable decision and repeat behavior                                                                                                                                                                                                                                                                                                   |
| ------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Decide an Approval                   | Bind the decision to the pending invocation and original prepared arguments/configuration. An identical saved decision returns that decision; a contradictory or stale decision conflicts and never becomes another execution. Cancellation/current stricter policy still prevents dispatch; a durable allow is not replay permission. |
| Request cancellation                 | Save the monotone request against the Turn while serializing with success publication. Repeats preserve the original decision and report current settlement separately. Known committed work remains committed. Inconclusive storage does not claim which decision won.                                                                |
| Delete an application-result payload | Authorized deletion changes payload availability and execution revision, not terminal outcome, receipt or comparison identity. Repeats report already deleted. This is not an API to erase Tool intent, recovery dependencies, history or all diagnostic data.                                                                         |
| Record reconciliation evidence       | Apply explicit compatible lookup evidence to the exact invocation under expected execution revision and current ownership. Missing/failed/inconclusive lookup is not proof that an effect never ran; delayed requests and eventual consistency must be excluded by the supported upstream contract before concluding absence.          |
| Acknowledge unresolved external risk | Require explicit authority, known history-commit state and exclusion of old publishers; preserve uncertainty and the decision. Do not label the external action undone or clear an unknown history commit. This remains the selected guarded abandonment path, not receipt deletion.                                                   |

Recovery selects from recorded facts, never from the absence of a final progress event:

| Confirmed record state                | Permitted next action                                                                                                                                                                                                                                        |
| ------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Acceptance with no entry intent       | Initial invocation with the same Turn/key, after current cancellation/ownership/budget and binding checks. No supported binding means paused work, not dropped work or a newly accepted Turn.                                                                |
| Entry intent with no terminal outcome | Continue only a compatible supported continuation; otherwise pause. The marker cannot establish that the first instruction did or did not run.                                                                                                               |
| Saved complete generation             | Reuse the recorded response under the validated continuation; do not generate it again merely to reconstruct local Tool work. Incomplete/unencodable/unknown responses do not grant local dispatch.                                                          |
| Pending Approval before Tool intent   | Restore the same ask/decision only if its prepared-argument binding can be reconstructed compatibly. Decoding again is not automatically equivalent to the originally approved value. Changed/unreconstructible arguments pause; no silent reuse of consent. |
| Tool intent without confirmed outcome | Treat as potentially executed, even if the process might have died before dispatch. Use an explicit supported reconciler or permitted idempotent/replay-safe retry retaining the original identity and upstream guarantees; otherwise retain the fence.      |
| Confirmed Tool outcome                | Reuse recorded outcome/payload where available. Deleted, unavailable or incompatible payloads are not authority to repeat a known effect.                                                                                                                    |
| Unknown conversation/success commit   | Resolve the authoritative write before terminal claims, abandonment or new admission. Current in-memory history and a lost ACK cannot decide it.                                                                                                             |
| Known terminal outcome                | Retrieve it and repair delivery/routing if needed. Separate unsafe-external-outcome fences may still block new work.                                                                                                                                         |

Saved compatibility information must identify the relevant program/continuation version, input/result codecs, Tool/preparation binding and behavior, Provider/Model request semantics, policy and instruction/Skill inputs used by unfinished work. A module path, display name or matching TypeScript signature is not proof of compatibility. Reacquire live resources; never serialize them or secret credential material. Changed credentials must still address the authorized original external subject where reconciliation/retry depends on it. Matching declared versions remain an author trust boundary, not proof of semantic equivalence; incompatible or unverifiable bindings pause rather than guess. Supported recovery intersects recorded permission with current policy, cancellation and budgets, never silently broadens it. Exact version declarations/encoding and the compatibility matrix remain specification work.

### Queued follow-ups, steering and budgets — candidate

**Selected defaults:** failure/cancellation pauses pending follow-ups; steering with no remaining Model safe point is reported not applied, never automatically enqueued; a custom Agent may catch a Step/Tool-count limit and deliberately finish valid work, while the default loop fails; a configured execution deadline includes Approval waits and downtime but not time spent queued. The following mechanics derive from those choices and the existing shared execution boundary, not a second scheduler/Agent engine.

#### Follow-up queue

- Keep one durable FIFO ordering per Transcript, ordered by successful enqueue decisions rather than network arrival or wall time. Each item is a separate Turn with its own input, key/receipt, captured encoded invocation input/selection/configuration, result and accounting. Use a versioned compatible input representation, not a serialized closure or silently recomputed mutable default. Queue acceptance does not acquire its execution Session/resources or claim that the Agent has started. The ordinary submit operation still rejects busy work; enqueue is explicit.
- Enqueue atomically checks key-first deduplication, current authorization, its observed shared position/active-work anchor and capacity, then records the item and ordered predecessor. A normal predecessor commit is the specifically authorized context advance: the next item runs from that committed outcome, not from an arbitrary later Branch. Appending behind pending work does not create private Session/Route heads. Reuse #170's authoritative recheck before returning preflight rejections.
- Only the eligible queue head may acquire normal Transcript/Route admission. An immediately submitted Turn cannot silently overtake ready queued work; it rejects rather than implicitly joining the queue. A paused queue does not itself own execution admission, but its fences remain binding and unrelated work does not automatically rebase it. Claim/dequeue uses the same conditional owner-side entry protocol as immediate work; a delivery retry or queue read never launches another copy. Recheck current cancellation, permissions, compatible bindings, budgets and fences. For queued work, admission acquisition, removal from pending eligibility and program-entry intent form one conditional durable claim, so no intermediate reservation bypasses a winning pause. Queued items remain unstarted until that claim is confirmed; ambiguous writes do not permit invocation.
- **Pause, do not silently rebase:** predecessor failure/cancellation, unresolved outcome, incompatible binding or unrelated execution-position change prevents automatic advancement. A manual Branch change pauses pending work rather than moving it to the new context. Manual pause and resume both target an explicit Transcript/queue and expected queue revision, require current Principal authority over every affected pending item, and reject stale or unauthorized requests rather than controlling newer work. Writer authority alone is not permission to control another Principal's work. Pause serializes with the next entry claim: if pause wins, subsequent dispatch stops; if entry was already claimed, that active Turn is unaffected and only later work can be paused after refreshing the revision. Resume additionally validates a fresh shared-position token and records its new anchor; it cannot clear a reconciliation fence or change another Principal's identity/permissions. Preserve original receipt/request and enqueue anchor: normal predecessor advancement or an explicit reanchor decision supplies the actual execution base, which becomes fixed at admission; do not rewrite original comparison data.
- Cancelling an unstarted item records cancellation without invoking it or deleting its receipt. Later items whose predecessor was cancelled pause at that gap; earlier eligible work need not be cancelled. Cancelling active work follows the existing requested-versus-settled protocol. No new admission or Branch switch follows merely from a cancellation ACK.
- Increment the queue revision atomically with membership changes (including enqueue/cancellation), claims, pause/resume decisions and anchor changes. This is separate from Transcript and Turn revisions; a snapshot cannot authorize a later control against an unseen membership or state. Explicit control retries with stale revisions query fresh state rather than blindly repeating the action.
- The queue is finite. Capacity counts pending retained items, including paused work; reject overflow without implicit waiting or dropping older items. Apply the selected count and encoded-input byte profile below; additional application/Principal ceilings remain to specify. No implicit restart loop, timer-based rebase, priority system or arbitrary dependency graph is required.

#### Steering

- Bind steering to the explicit current Turn and a stable input receipt; never retarget it to whichever Turn happens to be active on delivery. It contributes conversation input, not replacement function arguments, permission, cancellation, altered Tool parameters or a new Turn. Validate/authorize and durably accept it before acknowledging it as pending; duplicate delivery refers to the same input. Bound pending input count/bytes independently of lossy progress; overflow rejects without dropping accepted input.
- Consume eligible steering in accepted order at the next controlled pre-generation safe point, after the prior response/serial Tool group and required cleanup. Persist the association with that Step's planned input before requesting the Model. Steering during an Approval wait neither decides that Approval nor changes its prepared arguments; explicit cancellation is the separate stop control.
- Distinguish pending input, recorded inclusion in a planned Step, request dispatch/outcome and not-applied input. Planned inclusion alone is not proof that the Provider received or followed it. A crash must not include one steering input in two independently generated requests; supported continuation reuses the recorded association and obeys the same request-uncertainty rules as other generation.
- A custom Agent chooses whether to request another Step; steering cannot force arbitrary function code to do so. The default loop may consume pending steering at its normal continuation boundary through the same Step path. Serialize steering admission/Step association against Turn closure: close steering admission and record never-assigned inputs as not applied, so no late request can leave an orphan pending input. Preserve pending/unknown dispatch facts where an input was assigned but request delivery is uncertain; do not falsely mark it unused or silently enqueue a replacement Turn.

#### Budgets and deadline

**Selected configurable first-party profile:** 64 controlled Model generation calls and 256 local Tool dispatches per root Turn, including managed descendant work; 32 pending follow-ups and 16 pending steering inputs per Transcript; no execution deadline unless configured. Descendant admission is limited to four active/admitted-unsettled descendants, two levels below the root (root depth zero), and eight distinct accepted launches across that root's descendant tree. Duplicate accepted requests do not spend another launch; cancellation does not refund the cumulative accepted-launch count. These are starting defaults, not measured capacities, spending caps or fixed Core constants. First-party composition supplies them; native embedding supplies its policy explicitly.

**Owner-selected encoded-input profile:** 1 MiB per submitted application input, including queued Turn inputs; 8 MiB total pending follow-up input per Transcript; 64 KiB per steering input and 1 MiB total pending steering input per Transcript. These configurable finite bounds complement the count limits. Measure bytes of the declared encoded representation (UTF-8 bytes for text/JSON), not character count or decoded heap size. Include paused pending inputs in aggregate capacity and update byte/count reservations together with admission, removal and entry claims. Accepted matching retries reserve nothing again; new-work byte checks cannot override key-first retry precedence. Transport-envelope bounds still apply before parsing, with key-only authorized lookup available when a prior request cannot be resent under current transport limits. Reject overflow, never truncate input or drop accepted work. Removing input from pending eligibility releases pending capacity, not its durable receipt/comparison evidence. Separate bounds for transport envelopes, captured configuration, results and other stored payloads remain qualification/specification work; these limits do not claim to bound all memory or total retained storage.

Count managed summarization/Compaction generations and explicit generation retries, not just visible Agent-loop iterations; reusing a saved response is not a new generation. Provider-internal physical requests/fallback still require separate accounting qualification. The numeric limit does not falsely promise a maximum number of upstream HTTP requests or dollars. Shared root accounting cannot be reset by launching a fresh child Session or promoting work to application ownership. Explicit application-owned jobs additionally have a configurable first-party limit of **four admitted-unsettled jobs per application**, across originating roots/Principals; this does not grant authority over another Principal's jobs. The selected child acceptance ordering below reserves all applicable capacity together. Exact reservation/charge encodings and backend atomicity remain to qualify.

| Dimension                     | Accounting and stop behavior                                                                                                                                                                                                                                                                                                                                                                                                                          |
| ----------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Logical Steps                 | Track logical Step identity separately from generation charges. Reserve each controlled generation call before dispatch, including explicit retries and managed Compaction. Failed/interrupted dispatch does not erase consumption; saved-response reuse does not generate again. Track Provider-internal physical attempts separately.                                                                                                               |
| Local Tool dispatch           | Reserve before invoking the handler under its runtime identity. Reusing a recorded outcome is not a new dispatch; any permitted external retry is accounted separately. A response's remote calls are not falsely counted as locally gated execution.                                                                                                                                                                                                 |
| Usage / cost                  | Preserve reported usage, reservations and unknown amounts rather than treating missing usage as zero. Only advertise an enforceable hard limit where the qualified Provider/request boundary supplies the necessary bounds/accounting. Native fallback/retries and remote capabilities remain qualification gates.                                                                                                                                    |
| Configured execution deadline | Establish a persisted absolute deadline at the entry claim; queue waiting is excluded, Approval waits and downtime included. Resume does not reset it. Check expiry on entry/recovery and controlled boundaries and before success publication; expiry requests cooperative stopping and prevents a later winning success publication. Clock/dispatch uncertainty and uninterruptible cleanup remain explicit limitations, not a hard kill guarantee. |
| Delegation / recovery         | Carry accounting and applicable parent ceilings into supported child/recovery operations; no reset from reconnect, restart, retry or creation of a fresh Session. A rejected new reservation cannot consume the same logical operation twice on retry; previously dispatched/uncertain work cannot be refunded merely because its response was lost. Limits may be tightened, not silently reset or expanded during recovery. A separately accepted follow-up is a new Turn, but does not bypass application/Principal or parent-scope ceilings.

**Count limits versus cancellation:** reaching a Step/Tool-count bound blocks additional controlled work beyond that bound. A custom Agent may catch that condition, use shared read-only outcomes and return normally; commit still requires structurally valid completed staging, required cleanup and no cancellation/deadline/uncertainty barrier. The default loop does not manufacture success from exhaustion. Catching a failure does not make an unfinished Tool group valid, reclaim already consumed budget, extend a deadline or authorize replay. Arbitrary Effects outside controlled operations remain unsandboxed.

Other payload/envelope limits, additional scope-specific ceilings, precise usage reservation/reconciliation, clock assumptions and the versioned queue/control/budget representations remain specification work. These policies are not implemented or backed by new runtime tests; existing bounded Step/Host proofs do not establish durable queues.

### Declarative delegation — selected direction and remaining contract

**Selected authoring/runtime:** an explicit per-main-Agent catalog references ordinary child Agent functions; no folder discovery, automatic global registry, mandatory Agent class or separate engine. The catalog can carry native boundary metadata (description, input Schema and result projection/codec where actually needed). An optional adapter exposes only explicitly selected children through native Tools/Toolkits. Direct typed calls retain arbitrary live results/errors/requirements; mere import/catalog declaration performs no launch or child resource acquisition. The [optional adapter proof](../research/native-generation-boundary.md#optional-child-tool-adapter-and-nested-owner-correction) now combines explicit native Tool descriptors/projections with generated handlers through native `Effect.all`, without author-owned launch handlers, job maps or raw Scope plumbing. Original functions and selected direct types remain intact. A parent-discovered nested-owner bug is corrected at the shared child execution boundary: each child rebinds its internal owner inside its existing Turn, so descendants drain before the intermediate can commit. Independent source/log review and parent reruns cover the corrected surface, its preserved counterexample and effective mutation controls. Per-Turn binding of pure handlers is not infrastructure reacquisition. Candidate UUID handles are process-local and owner-bound, not durable admission/results or public exports; serviceful schemas, projection/encoding failures, closure races and the remaining #173 contracts still gate implementation.

Both **awaited** and **background** invocation are first-replacement requirements. Awaited delegation waits for that child's actual result/cleanup; background delegation returns its accepted-work identity/handle and lets the parent continue. A background return is not completion or a new ownership grant. Register background execution with its declared Turn/application owner, not the temporary launching Tool fiber, request or observer Scope; otherwise returning its launch receipt would cancel the work immediately. Parent-linked work is cancelled/drained when the parent Scope ends unless its result is explicitly joined earlier; required child failures propagate by joining, not through an all-child-failures supervisor. Rebind the internal managed owner at every child Turn entry: a descendant must not inherit an ancestor's owner and thereby outlive its immediate parent's required cleanup/commit boundary. Explicit application-owned jobs may outlive a parent Turn only with their own authorized ownership, closed resource dependencies, cancellation/result retrieval and recorded accounting. Do not silently detach to escape a deadline, parent policy or root limits. Neither mode accepts raw synchronous/Promise authoring instead of ordinary Effect functions, and neither implies subprocess or distributed execution.

A fresh child Session/Transcript remains the default; input/history projection is explicit and does not automatically append parent history, uncommitted staging or Skills to the child's Prompt or widen declared Tool permissions. This is not runtime Context isolation: native service references may be inherited, and phantom R is not a permission or secret filter. Explicit history forks and separately owned jobs retain their existing gates. A conversational fork does not fork the filesystem. Child availability and effective permissions are separate: selecting a named child must not widen the parent's recorded/current ceilings or acquire human Approval authority. The child authority and durable-operation contracts below constrain that boundary; concrete APIs and enforcement remain #173 qualification work.

**Selected coding-workspace policy:** concurrent readers, one managed writer per workspace including the parent. A parent waiting for a child cannot retain a conflicting writer claim and simultaneously grant that same workspace to the child; the ownership/handoff protocol must avoid this deadlock and reject conflicting work rather than silently run parallel writers. Explicitly supplied independent worktrees may write concurrently; no automatic creation, dirty-tree copying or merging. Workspace identity/claims belong to optional coding infrastructure, not a mandatory Git dependency in Core. Managed coordination is not an OS sandbox, consistent read snapshot or rollback; trusted arbitrary code can bypass it. Claim release requires actual settlement and sufficient evidence that an earlier writer cannot continue mutating that workspace, not a cancellation ACK.

Use the selected root-wide limits above for admission/accounting; no implicit unbounded child queue on capacity exhaustion. Completed/cancelled launches still count toward the cumulative eight; only reusable active capacity is released after actual settlement. Persist parent linkage, stable launch identity, exact accepted input/binding, ownership, result availability and accounting before promising durable acceptance. Retries must resolve existing accepted child work before applying new-capacity checks, and cannot launch it again. Child results do not automatically become parent Messages or new follow-up Turns. The selected contracts below reuse shared execution records and controls; their concrete representations and runtime enforcement remain unqualified.

#### Child authority and Approval

**Owner-selected:** children use the application's existing authorized consent capability/channel, with child identity and ancestry visible. This does not require a Host in direct embedding or make the parent Model an approver.

- At admission, bind the selected child/program, originating authority, explicit input/history/Skill projection and requested capabilities. Effective authority is the intersection of applicable recorded ancestor ceilings, current application/Principal policy, the delegating operation's grant and the child's declared restrictions. Descendants cannot widen it. A child may expose specialized Tools not shown in the parent's Prompt only within that delegable authority; neither Tool-name equality nor inherited Context services establish permission.
- Separate availability, permission and consent. Approval to launch a child authorizes only that launch and its bound scope, not all later child Tools or Provider capabilities. Apply ADR-0051 inside each child: stricter policy wins, missing consent denies, and neither child nor parent Model can decide a human ask merely by possessing its ID. Each ask binds the child Turn, exact invocation/prepared arguments and responsible authority; route it through the configured consent capability, not whichever observer or TUI happens to be connected. Reconnect/duplicate decisions use the same shared authenticated control protocol.
- Recheck current authority, cancellation, deadlines and fences at controlled dispatch/recovery boundaries. A recorded allow does not override revocation or an incompatible policy binding. These checks do not re-decode approved arguments or rerun the same prepared Tool's author/risk decision. Denial or an unavailable compatible binding cannot silently broaden authority. Trusted ordinary Effects remain unsandboxed; this contract governs managed operations, not all service access.

#### Durable child admission and results

- Use one shared conditional acceptance protocol, not a child scheduler/receipt store. The launch identity binds application/authority, originating root, immediate parent, selected child, requested ownership and exact accepted input/bindings. A Provider call ID, function name or process-local Fiber handle is not that identity. Supported continuation retains the recorded launch operation; repeated ordinary calls are distinct unless they explicitly address the same retry identity. Existing authorized retries resolve before new capacity, parent-open or current-selection checks; changed requests conflict. An inconclusive lookup cannot establish absence.
- Acceptance atomically records the child Turn/Transcript reference, immutable parent/root linkage, selected owner, comparison/compatibility inputs and applicable capacity/launch reservations. For a new delegation, recheck that the originating parent is still open as well as the selected owner, plus ancestry/depth, permissions, deadline, workspace availability and budgets in the winning decision. Even application-owned work cannot be newly delegated through a closed parent; if its acceptance wins first, subsequent parent closure does not cancel that separately owned job. An ambiguous acceptance write permits neither a second child nor function entry. There is no implicit waiting queue for new child work that cannot obtain capacity or a workspace claim.
- A confirmed exclusive entry intent precedes invoking the child. Owner closure/cancellation serializes with admission and entry: it either prevents new work or includes the already accepted parent-linked work in cancellation/draining. Track accepted-but-not-yet-forked children as well as live Fibers; a native fork alone cannot close this durable race. Cancellation before entry records a terminal unstarted outcome; after entry intent, absence of a live Fiber/return is not proof that the program never ran. Unsupported arbitrary-program recovery pauses rather than restarting the function. Lookup, join and result retrieval never launch.
- Each child commits its own successful Turn only after required cleanup and encoding of any promised durable result, using the normal atomic history/outcome publication. A later parent failure does not roll that child history or its external effects back. Direct live results/errors retain their native types and identity. Durable input/comparison data needs an explicit compatible representation; live-only delegation does not automatically serialize arbitrary inputs. Durable acceptance alone does not promise a serialized application result: record whether a result was promised and its explicit codec/projection. If a continuation needs that result after restart, it must have a compatible retained representation; otherwise it pauses. Deleted, incompatible or unpromised results never authorize rerunning the child. A parent Tool's later projection/encoding failure does not undo an already committed child.
- Ordinary known unjoined child failure is still not an automatic parent failure. Separately, undrained work, unresolved child commit or unsafe external-outcome uncertainty blocks affected parent-linked ancestor success/reuse and shared-resource reassignment. Propagate the safety fence transitively without wrapping every child failure into a supervisor error. Terminal status, cleanup settlement and reconciliation state are distinct; a cancellation ACK or failure label alone releases neither unsafe capacity nor writer claims.

#### Explicit application-owned jobs

**Owner-selected:** an explicitly application-owned job survives normal completion, failure or cancellation of its originating parent Turn. It is separately cancelled through an authorized job control, or stopped/drained by application shutdown. Ordinary parent-linked children retain their existing cancellation behavior. Ownership is immutable at acceptance; there is no after-the-fact detach/promotion to evade stopping.

- An ownership boundary changes lifetime/cancellation, not ancestry or authority. Retain original parent/root links and the original root's shared generation/dispatch/launch/depth accounting after that root finishes. Count the job against root descendant capacity and the application-wide job limit in the same acceptance decision; another separately owned descendant consumes another job slot. Parent-linked descendants stay under their immediate managed Turn owner. A terminal origin does not mint a fresh ledger, refund spent work or change the child's recorded Principal.
- Preserve applicable absolute ancestor deadlines and permission ceilings; parent cancellation independence does not extend a deadline or bypass current policy. Application-owned work must use application-owned/closed resource dependencies, never retain a released parent Session, Turn Scope or invocation-only consent dependency. Application shutdown closes admission before cancelling/draining jobs and releases infrastructure only afterward.
- Release a job's reusable capacity only when its owned work and parent-linked descendants have settled and relevant uncertainty is reconciled; cumulative accepted-launch consumption is not refunded. Separate application-owned descendants retain their own slots/owners. Matching retries consume no additional slot. The selected app-wide limit is in the shared budget profile above; there is no overflow queue.
- A confirmed application-job receipt can be the parent's completed launch result while the job remains unfinished; it is not job success. Later job failure/uncertainty does not retroactively undo that parent commit. Keep job-owned and affected shared-resource fences, accounting and authorized queries independently available. Uncertainty about whether the launch itself was accepted still uses the parent's ordinary Tool/acceptance reconciliation barrier.

#### Explicit workspace handoff

**Owner-selected:** delegation never implicitly transfers a writer claim. A managed handoff must be explicitly requested; afterward parent writes remain blocked until the child settles and the parent explicitly reacquires. Conflicts reject rather than wait, including awaited delegation that would otherwise deadlock with its parent.

- Optional coding infrastructure binds claims to a stable workspace/resource identity, canonical root and current owner/revision, not a Model-supplied label or raw path string. Different labels, symlink/case aliases or overlapping nested roots cannot acquire independent writer claims for the same controlled files. Explicit worktrees permit independent file writers only where resources are actually independent; shared Git metadata or other shared mutation targets need their own applicable coordination. Core has no mandatory Git/worktree dependency.
- Handoff first stops new managed writes under the old claim and drains admitted mutations, including owned processes capable of further writes. It then conditionally transfers the claim under current authority and expected ownership/revision, and records the recipient binding. A child admission and its required transfer/reservation must not leave a runnable child without the claim. Lost acknowledgements require reconciliation before either owner writes; no timeout-based stealing or release from a cancellation ACK.
- After transfer, stale parent/descendant claim references cannot authorize another managed mutation. When the child settles, release does not automatically revive an earlier parent claim. Explicit reacquisition checks current ownership, policy and fences; failed/uncertain child cleanup prevents unsafe reassignment even if the child reports a terminal outcome. Readers still receive no consistent-snapshot guarantee, and neither handoff nor failure rolls filesystem changes back.

Fresh-context read-only prose review found no issues in this bounded draft against the shared contracts and ADRs; it did not execute tests or inspect historical proof artifacts. These are selected policy and required ordering, not executed race/crash/containment tests. Exact operation signatures, compatible stored representations, real-backend atomicity, stale-owner exclusion and process/filesystem enforcement still gate implementation. Reuse the shared Turn/ownership/Approval/query machinery; do not build a second delegation engine.

### Contract scenarios — required checks, not executed evidence

- Two identical-key requests both initially miss. Pause B before preflight while A accepts (busy case) or accepts and commits (stale-position case). B must find A's receipt before returning its new-work rejection; repeat with a changed current input decoder and an unavailable authoritative recheck. An existing authorized match wins, while inconclusive lookup cannot claim absence. A changed request conflicts. A rejection decided on confirmed absence may precede a later acceptance; response delivery order is not the decision order.
- An acceptance write loses its ACK: no program call until confirmation; an inconclusive lookup is not absence. A retry after Route movement or code change still finds authorized original work without running a new decoder.
- Two owner-side launch attempts race for one accepted Turn: only the confirmed entry-claim winner calls the function. Then crash immediately after entry intent but before that call: pause arbitrary custom work; do not infer non-execution from the missing return or lack of Tool records.
- One view selects another Branch and then selects the old head again: the old position token stays stale. A second Session/Route cannot keep a private execution head for that Transcript.
- Tool A succeeds, Tool B fails with typed `QuotaError`: the Agent catches `QuotaError` from native E and reads A's success payload through the query. B's record shows only a safe failure classification (plus an encoded payload if a codec was declared), never the live `QuotaError` or a wrapper; remote callers see only the classification. No completed partial Step or malformed conversation is manufactured; reading records does not clear uncertainty.
- Cancellation wins before the entry claim: do not invoke the Agent function. If entry was already claimed, cancellation remains cooperative. While cleanup is held, queries report requested cancellation and unsettled execution separately; no new Turn or Branch switch is admitted from the ACK.
- A snapshot of Turn `t7` at execution revision 20 shows success with an available result, and page 1 of its Tool records is read at revision 20. An authorized deletion then produces revision 21: page 2 requested at revision 20 returns `revision-changed`, and the payload read returns `deleted`. Terminal success, receipt and comparison identity are unchanged; nothing reruns.
- Reconciliation lookup returns not found while the original remote request may still arrive: retain uncertainty unless the qualified upstream contract establishes definitive absence.
- A stale owner attempts to publish after restart: reject using current writer authority even if its history head still matches. The owner-exclusion mechanism must pass the real backend/crash tests before this is a guarantee.

Worked identity, comparison and query checks (design examples, NOT runtime tests). Request `R` is `{kind: execute, target: route chat-9, expected: (T1, m7, r12), input: {"text": "fix"}}` with Model omitted.

- **Lost ACK after commit:** `R` under key `k1` is accepted as Turn `t1`; the response is lost; `t1` commits and the Transcript reaches `r13`. Retrying `R` under `k1` finds the receipt first, matches under its stored comparison version and returns `t1` with its committed outcome. The stale `r12` token is not rechecked, and no Agent, decoder or entry claim runs.
- **Changed retry:** after a refresh the client resends under `k1` with `(T1, m8, r13)`, or adds the currently default Model explicitly; both conflict. Reordering object members in `input` still matches; reordering array elements does not.
- **Rejection binds nothing:** `R` under `k2` is rejected as stale on confirmed absence, so no receipt exists. A refreshed request under `k2` is accepted as `t2`. The delayed original `R` under `k2` now conflicts rather than receiving another stale rejection.
- **Absent is not a reservation:** two clients of one Principal race. Client A resolves `k3` as `absent`; client B's submission under `k3` then wins acceptance; A's different body under `k3` conflicts. Neither A's read nor its preflight entitles it to new work.
- **Inconclusive lookup:** the lookup for `k4` times out while the Transcript is also occupied. Report outcome unknown, not an occupied rejection (which would imply confirmed absence) and not acceptance.
- **Retired comparison version:** `k5`'s receipt was stored under comparison version v1 and a later library supports only v2. An identical retry is `incomparable`, not a conflict that could push the client to a new key and duplicate work; key-only resolution still returns `t5`.
- **Revoked access:** `k6`'s stored target becomes inaccessible to its Principal. Resolution and an identical resubmission both report not accessible; neither becomes new work, and restored access returns the original `t6`.
- **In flight versus unknown:** Tool B has intent and no outcome. While its owner is confirmed active the query reports in flight; after a crash without confirmed owner exclusion it reports outcome unknown. Neither clears the fence.
- **Non-durable release:** with persistence opted out, the same queries read `t8` while its owner lives, each response marked non-durable and the application result `not-promised`. After release they return `released`; they neither reacquire the program nor rebuild records, and no receipt survives to make a later retry safe.
