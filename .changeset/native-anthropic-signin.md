A Provider's credential descriptor can name an API-key variable and an Auth capability together, `{ env, capability }`, for a Provider that reads an API key when one is set and otherwise its sign-in, and the capability can name the `profile` it acts on. `Provider.make` checks the variable's name, and the descriptor schema rejects an invalid one instead of dropping it. `mitome auth status` prints such a Provider's variable as present or missing and that a sign-in is available, without reading it; `mitome auth login` and `logout` run its sign-in for the descriptor's profile, interrupt the capability when interrupted, and exit with the exit status a capability fails with when it is from 1 to 255, otherwise 1. `AuthenticateOptions` gains `profile`.

`anthropic()` also accepts the Claude Console sign-in. An API key in `ANTHROPIC_API_KEY` (or `apiKeyEnv`) still wins and is sent unchanged. Without one, it reads the profile Anthropic's CLI writes with `ant auth login --profile=mitome` (the new `profile` option names another) from Anthropic's config directory, sends its access token as a bearer token with the `oauth-2025-04-20` beta beside the request's own betas and the profile's workspace, and refreshes the token as Anthropic's SDK does, with the client id the profile records, rewriting the credentials file atomically under a lock next to it, unless `ant` replaced or removed it during the refresh; concurrent requests through one Model share one refresh and its outcome, and a refresh request once sent is written even if its caller is interrupted. A token the API rejects is replaced once, by a fresh token already on disk or a refresh, and the request sent once more with a different token. The profile's tokens go only to an https host or to http on this machine, and a `base_url` or `baseUrl` that is set but unusable is an error; the refresh token goes only to its issuer, the profile's `base_url` or else Anthropic's API, never to the `baseUrl` option's host; a profile changed during a Session fails its requests until the Session restarts. Token refreshes are not counted as Model requests. Both Credentials bill the Console organisation at API rates. `mitome auth login --provider anthropic` and `logout` run `ant auth login` and `ant auth logout` for the Provider's profile, stopping `ant` when interrupted, `login` saying that `ant` makes it the active profile; Mitome runs no OAuth flow and holds no client id. The Claude subscription sign-in is not supported.

Without either Credential, including a profile signed out of, Model provisioning fails with `MissingCredentialError`, whose message now also names the sign-in. A profile that cannot be used fails provisioning with the new `UnusableProfileError`, exported from `@mitome/providers/anthropic`, and one that stops being usable during a Session fails the request with an `AiError`; each message says what to fix. A refresh the token endpoint rejects as an invalid grant asks to sign in again, unless `ant` signed in again during the exchange, whose credentials are then used; a 429 or 5xx is reported as a temporary, retryable failure; any other answer is reported as a broken token endpoint. No value the endpoint returns is copied into a failure but its status and a known OAuth error code. The Codex credential store sets the mode of its replacement `auth.json` to 0600 on the open file before renaming it, so it is private under any umask, and waiting for its lock can be interrupted.

`mitome init` for Anthropic prints the API key and `mitome auth login --provider anthropic` as alternatives, and its README says where `ant` keeps the sign-in. The Anthropic choice of `mitome init` and `create-mitome` says it can sign in: the Configuration's README gives `mitome auth login --provider anthropic` beside the API key, and an application's README gives `ant auth login --profile=mitome`. `ProviderChoice.signIn` carries either the import of the Provider's `login` or, as for Anthropic, the `appCommand` an application runs once.
